1. 项目概述

1.1 选题背景

教师提供了 827 类汽车、共 103,785 张图片的数据集，但没有给任何价格、配置、口碑等文字信息 —— 数据集只有"类别 ID + 车型名"。

而"看车"这件事，用户真正关心的是：这是哪款车、多少钱、有哪些配置版本、我什么时候看过它。

于是我们把选题定为 「识车档案 CarDex」：一个私人车型资料库 —— 拍一张车，认出它是什么；查它的资料；记下"我看过这辆车"。

为什么不做成"通用车辆识别 API"：那样会变成"能认 827 类但什么都不深"的工具。 私人资料库的定位决定了三件事： ① 选类要贴合私人用户会看会记的车（不要重卡、牵引车）； ② 必须能"如实说不知道"（用户拍到陌生车是常态）； ③ 要有"档案"的积累感（看车记录、档次知识库）。

1.2 目标用户

用户 场景 核心诉求
准备买车的个人 路上/停车场看到一辆车，想知道是什么、多少钱 快速识别 + 价格参考
汽车爱好者 想系统了解某款车的各配置版本差异 档次对比、参数差异
普通记录者 想记下自己看过/试驾过的车 看车档案、随时回查

共同特征：都不是专业用户，不需要"专业级"的精确度，但非常不能接受被编造的答案。 这一条直接决定了后面所有关于「反编造」的设计。

1.3 使用场景

场景 A：路边看车

用户拍照上传 → 智能体识别出"日产_轩逸" → 从档案库返回品牌、车身类型、简介、看点标签。

场景 B：问价格与配置

"轩逸有哪些配置版本？豪华版比舒适版贵多少？" → 开启联网 → 智能体自己决定 搜索 → 打开报价页/配置页 → 抓取档次表 → 存入档案库 → 回答差价与配置差异。 下次再问，不联网也能答（知识已经沉淀）。

场景 C：陌生车

拍到一辆不在库里的车 → 智能体如实告知"这个不在我的资料库里"，而不是硬认一个。

场景 D：记录看车

"把刚才那辆车记下来，我看中的是舒适版" → 存入个人档案，之后可检索、可统计。

1.4 主要功能

功能 说明
车型识别 自训练 51 类视觉模型（50 款车型 + unknown），带拒识与低置信度提示
车型资料查询 品牌、车身大类/细分、简介、看点标签、训练样本量
档次知识库 各配置版本的价格、参数、档次间差异（联网采集后沉淀，可离线复用）
个人看车档案 记录、检索、备注、删除、按品牌/车身类型统计
联网搜索与浏览 搜索 + 真实浏览器打开网页读取渲染后的内容
Web 交互界面 会话侧边栏、API/模型配置面板、图片上传、流式输出、工具调用可视化

2. 数据分析

2.1 从 827 类中选择 50 类的理由

选类原则写成了代码（src/select_classes.py），不是手工挑的：

原则 内容 为什么
P1 主题契合 只选私人用户会"看、比、记"的乘用车与轻型商用车型，排除重卡/牵引车 贴合"私人资料库"定位
P2 车身类型覆盖 轿车 / SUV / MPV / 跑车 / 微面 / 轻客 六类都有代表 保证资料库的横向检索能力
P3 品牌多样性 覆盖 37 个品牌；同品牌最多 2 类，且车身形态差异明显 降低同品牌族内混淆
P4 单车系单一代表 同一车系的衍生版（探岳 / 探岳X / 探岳GTE）只取一个 避免近重复类别互相压制 Macro-F1
P5 样本充足 训练样本 ≥ 80 张、验证样本 ≥ 26 张 每类都能学到稳定特征
P6 造型辨识度 优先选设计语言差异大的车型（方盒子越野、超跑、微型电动车、豪华旗舰） 提升类间可分性

P4 是 Macro-F1 的关键。评分是 51 类等权平均，把"探岳"和"探岳X"都选进来， 这两类会互相吃掉对方的 F1，等于人为给分数设了个天花板。

2.3 unknown 样本的来源类别与采样方法

unknown 的构造是这类拒识任务最容易出错的地方，我们设了三条硬约束 （全部记录在 configs/unknown_sources.json，可追溯）：

来源类别    98 个（34 个同品牌近似款 + 64 个其他品牌）
train 采样  每类 20 张 → 1,960 张
val  采样   每类  6 张 →   588 张

三条约束：

  1. 来源类别与本组 50 类完全不重叠 —— 脚本内有断言校验；
  2. train / val 样本不重复 —— train 取自来源类别的训练图片，val 取自来源类别的验证图片；
  3. 完全不使用测试图片。

关键设计：34 个"近似款"（hard_negative）

{ "id": "0702", "name": "MINI_MINI CLUBMAN",
  "source_kind": "hard_negative", "target_class_id": "0264" }   // 0264 = MINI_MINI

这不是随便选的：MINI CLUBMAN 和 MINI 外观极像，就是要考模型能否分辨"像但不同"。

如果 unknown 全是卡车、飞机，模型闭着眼都能拒识，这个指标就没有意义了。 实测数据证明这个设计有效：hard_negative 的误拒率 12.7%，是其他品牌 unknown（2.9%）的 4.4 倍。

unknown 占比： train 26.2% / val 24.3%。

2.4 数据质量检查

检查项 结果
图片损坏 0 张（9916 张全部可正常打开）
完全重复（MD5 相同） 1 组，涉及 2 张
其中跨 train/val 重复 0 组 ← 最要命的一类泄漏
类内近重复（dHash 汉明距离 ≤ 5） 0.00%
图片尺寸 1,730 种唯一尺寸；最常见 667×500
宽高比 0.45 ~ 3.02，均值 1.42（多数接近 4:3 / 3:2）→ 采用等比缩放 + 中心裁剪

跨 train/val 的 MD5 重复为 0，说明没有"同一张图既训又测"的泄漏。

2.5 预处理与数据增强

预处理（训练 / 评估一致）

评估：Resize(短边到 size×256/224, 双线性) → CenterCrop(size) → ToTensor → Normalize
归一化用 ImageNet 的 mean/std —— 与预训练权重配套，不能换

四档增强策略（强度递增）

档位 组成 用在
baseline_train RandomResizedCrop(scale 0.5~1.0) + 水平翻转(0.5) 基线实验
moderate_train 上面 + ColorJitter + RandomErasing(0.25) 微调（温和）
strong_train 上面 + RandAugment(2, 7) + RandomRotation 主实验

几个刻意的选择：

  • ColorJitter 的 hue 只给 0.08 —— 色相变化过大会把白车变绿车，反而不合理；
  • RandomErasing 必须放在 ToTensor 之后 —— 它的操作对象是张量；
  • 归一化必须用 ImageNet 的 mean/std —— 用了 ImageNet 权重就必须配套，否则特征分布对不上。

3. 模型设计与训练

3.1 模型结构

骨干网络（src/cardex/models.py）：

架构 参数量 本项目用途
ResNet18 ~11.2 M 基线 / 主实验 C1
ResNet50 ~25.6 M 主实验 C2、最终模型
Wide ResNet50_2 ~68.9 M 备用（未启用）

分类头改造（迁移学习的关键一步）：

model = factory(weights=weights)          # 加载 ImageNet 预训练
in_features = model.fc.in_features        # ResNet18: 512, ResNet50: 2048
model.fc = nn.Linear(in_features, 51)     # 换成 51 类输出

为什么选 ResNet 系列： ① torchvision 官方实现，权重来源清晰；② 结构简单、训练稳定，适合 CPU/单卡环境； ③ 残差连接让深层网络可训练；④ 在细粒度分类上是成熟基线。

最终模型是集成（2 个成员，均为 ResNet50）：

成员 输入尺寸 角色
r50_288_from_scratch 288×288 中等尺度视角
r50_352 352×352 高分辨率视角

3.2 预训练权重来源

只用 torchvision 官方 ImageNet 预训练权重，代码里写死常量并注明版本：

SUPPORTED = {
    "resnet18": (models.resnet18, models.ResNet18_Weights.IMAGENET1K_V1),
    "resnet50": (models.resnet50, models.ResNet50_Weights.IMAGENET1K_V1),
    "wide_resnet50_2": (models.wide_resnet50_2, models.Wide_ResNet50_2_Weights.IMAGENET1K_V2),
}
  • 没有使用任何现成的汽车分类模型；
  • 没有调用任何第三方在线图片识别服务；
  • ImageNet 的 1000 类里不含任何具体车型，是通用视觉特征。

踩过的坑：ResNet50 的 V2 权重文件是 resnet50-11ad3fa6.pth，本机缓存里只有 V1（0676ba61）。 写错版本会触发联网下载并失败，所以把版本钉死成常量。

3.3 训练配置

主实验 C1（ResNet18 @224）：

{
  "arch": "resnet18", "image_size": 224, "epochs": 18, "batch_size": 32,
  "optimizer": "sgd", "lr": 0.01, "momentum": 0.9, "weight_decay": 1e-4,
  "head_lr_mult": 1.0,
  "scheduler": "cosine", "warmup_epochs": 2,
  "label_smoothing": 0.1,
  "ema_decay": 0.999,
  "mixup_alpha": 0.2, "cutmix_alpha": 0.5, "mix_prob": 0.35,
  "grad_clip": 5.0, "amp": true, "tta_hflip": true, "seed": 42
}

关键技术点：

技术 作用
线性预热 + 余弦退火 预热防初期震荡，余弦平滑收敛（按 step 调度，粒度更细）
bf16 混合精度（CPU）/ fp16（GPU） CPU 约 1.5× 加速；损失在 float32 中计算
MixUp + CutMix（prob 0.35） 样本混合增强，只对 35% 的 batch 生效
标签平滑 0.1 抑制过度自信，利于拒识
权重 EMA（0.999） 保存的是 EMA 权重，平滑训练噪声
梯度裁剪（5.0） 防偶发梯度爆炸
TTA（水平翻转） 在 log-softmax 空间取平均（几何平均）

踩过的坑（都写进代码注释了）：

  • head_lr_mult=10 + lr=0.01 → 训崩（val_loss 2889、Macro-F1 0.007），改成 1.0；
  • DataLoader(num_workers>0) 在受限环境下会 PermissionError，改用 0；后来在 GPU 上实测 num_workers=0 会让 GPU 79% 的时间在等数据，改成按设备区分默认值。

3.4 模型选择依据

选择流程：

  1. 候选：5 组对照实验 + 后续的分辨率实验，各自独立训练；
  2. 评估：在验证集上算 51 类 Macro-F1；
  3. 标定：每个候选在验证集上扫 (τ, t) 二维网格（τ ∈ [−0.4, 0.6] 步长 0.1； t ∈ [0, 0.6] 步长 0.05），按 Macro-F1 取最优点；
  4. 选优：按标定后的 Macro-F1 排名；
  5. 集成：把多个强模型做 log-softmax 几何平均。

最终结论：

冠军 = r50_288_from_scratch + r50_352，τ = +0.10，t = 0.20，中心+五裁剪 TTA 验证集 51 类 Macro-F1 = 0.9815

4.2 增益归因

改动 增益 说明
160 → 224 分辨率 + 强增强 + 正则化组合 +0.0998 最大的一次跃升
ResNet18 → ResNet50 +0.0082 骨干容量
224 → 288 分辨率 +0.0160 细粒度任务的关键
288 → 352 分辨率 +0.0029 收益递减
多裁剪 TTA（10 视角） +0.0025 推理侧零训练成本
对比学习（SupCon） 单独 +0.0002 / 作为集成成员 +0.0010 特征空间可分性 +29%，错误模式与基线不同
双强模型集成 +0.0009 需要成员"同样强"

关键结论：分辨率是最大的杠杆（合计 +0.117），远大于换更大的骨干（+0.008）。 车型识别是细粒度任务（A6 vs A6L 差在后门长度），224×224 下这些特征只剩几个像素 —— 模型不是不够聪明，是看不清。

反面结果（同样重要）：

手段 结果 原因
多尺度 TTA ❌ +0.0005 训练/测试分辨率不匹配，224 训的模型在 288 上掉点
快照集成 ❌ −0.0017 同一次训练的快照相关性太高、强度不齐
调低拒识阈值 ❌ −0.0011 当前值已是最优
弱模型加入集成 ❌ −0.003~−0.01 等权平均里弱成员是负资产
Energy-based OOD ❌ AUROC +0.029 但 Macro-F1 −0.001 OOD 判别力更强，但阈值与分类决策边界对不齐
Mahalanobis OOD ❌ Macro-F1 −0.001，AUROC 也更差（0.779） 特征空间方法在这个任务上不占优

4.3 混淆矩阵与错误分布

最终模型的错误结构（61 张 / 2422，占 2.52%）：

错误类型 张数
已知类被判 unknown 46
unknown 被误认成某个车型 25

错误最集中的真类：

真类 错误张数
unknown 25
大众_朗逸 6
福特_福克斯 5
日产_轩逸 4
红旗_红旗E-HS9 / 本田_奥德赛 / 奔驰_奔驰GLE 各 3

错误性质分析：

  • 错误样本置信度中位数 0.498，其中39 张置信度 > 0.5 —— 是系统性混淆，不是"模型没把握"；
  • 只有 6 张置信度 < 0.2。

修正过程中的一个重要发现：

早期我们以为"65 张已知类被误拒"是阈值问题，但细分后发现： 只有 7 张是被阈值卡掉的（且它们的 argmax 本来就错），另外 58 张是模型的 argmax 自己就选了 unknown。 所以调阈值毫无用处 —— 实测把 t 从 0.20 降到 0.15 反而从 0.9646 掉到 0.9635。

4.4 错误样本举例

例 1：unknown → MINI_MINI（置信度 0.972）

我们打开图片直接看了：那是一辆黄色的 MINI，圆形大灯、黑色轮眉、镀铬门把手、圆形油箱盖。

但它来自源类别 0702 = MINI_MINI CLUBMAN，是刻意挑选的 hard_negative —— 设计意图就是考模型能否把 CLUBMAN 和普通 MINI 分开。

这不是模型"瞎认"，而是一个"可以理解的错误"：两者外观极像。 正确行为是拒识，但难度确实很高。这类错误占 unknown 错误的绝大多数。

例 2：日产_轩逸 recall 偏低（0.886）

初版模型上轩逸的 F1 只有 0.875，是 50 个已知类里最差的之一。 分析发现是漏判（高 precision + 低 recall）。提高分辨率到 288 后升到 0.925 —— 说明细粒度特征（前脸格栅、大灯轮廓）在 224 下确实不够用。

4.5 测试集泛化的验证

客观限制：教师只提供了 train / val，没有提供测试集。 而我们在这条路上做了大量 基于验证集的选择 —— 扫 τ/t、比较 6 种集成组合、试 3 种 TTA 档位。 每一次"在验证集上挑最好的"都会让验证集分数偏乐观。

所以我们主动量化这个偏差（tools/verify_generalization.py），而不是回避。

4.5.1 五折交叉验证

做法：把验证集分 5 折，在 4 折上扫 τ/t，在留出折上评估 —— 这模拟"用一批新数据标定、拿到另一批新数据上用"。

折 标定集 标定出的参数 留出折 Macro-F1
1 1937 张 τ=+0.1, t=0.20 0.9801
2 1937 张 τ=+0.1, t=0.20 0.9818
3 1938 张 τ=+0.1, t=0.20 0.9897
4 1938 张 τ=+0.1, t=0.20 0.9713
5 1938 张 τ=+0.1, t=0.20 0.9834
平均 0.9812 ± 0.0059

与验证集上报出的 0.9815 相差 −0.0003 —— 差距几乎为零。

结论：标定没有明显过拟合。0.9815 不是在验证集上"刷"出来的。

每折 ±0.006 的波动反映的是抽样噪声（每折只有约 484 张，样本量小）， 不是模型不稳定 —— 平均值与全集结果几乎完全一致就是证据。 同时它也说明：验证集只有 2422 张，单次评估的精度极限大约就是 ±0.006， 讨论 0.001~0.002 的差异时要谨慎。

4.5.2 更严格的"完全诚实流程"压力测试

第一项只检验了标定的过拟合。但我们的模型选择（TTA 档位、集成组合） 也是在验证集上做的。所以做了第二项：

每一折不仅重新扫 τ/t，还在 4 种配置里重新挑冠军，再看它在留出折上的表现。

4 种候选（全体标定）：
  288+352@多裁剪   0.9815
  352@多裁剪       0.9806
  288@多裁剪       0.9779
  288+352@hflip    0.9789

折 1~5 全部选中「288+352@多裁剪」→ 平均 0.9812 ± 0.0059，差距 −0.0003

5 折全部选中同一个配置 —— 说明我们的选择流程是稳健的， 不是"试了很多组合碰运气碰上的"。换个数据子集，同样的流程会选出同一个模型。

4.5.3 鲁棒性压力测试（模拟真实拍照条件）

在 606 张子集上施加各种扰动，看性能掉多少：

扰动 Macro-F1 相对原图 判断
原图 0.9892 — 基准
JPEG 质量 30 0.9879 −0.0013 ✅ 几乎无影响
亮度 ×0.6 0.9870 −0.0022 ✅
亮度 ×1.5 0.9850 −0.0042 ✅
旋转 10° 0.9829 −0.0063 ✅
高斯模糊（半径 2） 0.9220 −0.0672 ⚠️ 明显下降
低分辨率（短边 96px） 0.4904 −0.4988 ❌ 灾难性下降

三条结论：

  1. 对常见拍摄差异很鲁棒 —— JPEG 压缩、曝光变化、轻微手抖旋转的影响都在 0.007 以内。 这印证了数据增强的设计有效（ColorJitter、随机裁剪确实学出了尺度/亮度不变性）。

  2. 对模糊敏感 —— 高斯模糊掉 0.067。真实场景中"运动中抓拍""没对上焦"会落入这一类， 属于需要改进的方向（可通过加模糊增强缓解）。

  3. 对分辨率极其敏感 —— 低清图直接崩盘（0.49）。 这反向印证了本文最重要的结论：本任务的第一要素是分辨率。 96px 时车前脸细节完全丢失，模型只能瞎猜。 实践建议：客户端应拒绝过小的图片，或提示用户重拍。

4.5.4 泛化能力的总结

维度 结论
标定过拟合 几乎没有（−0.0003）
模型选择过拟合 几乎没有（5 折选中同一配置）
对拍摄条件变化 鲁棒（压缩/亮度/旋转 ≤0.007）
对图像质量下降 模糊 −0.067，低分辨率 −0.499
单次评估的噪声 ±0.006（受限于 2422 张的验证集规模）

诚实说明：交叉验证给出的是"如果换一批同分布的新数据，能拿到多少"的估计， 它不等价于一个真正没参与过任何选择的独立测试集。 教师提供测试集后，应当用它做最终确认，而不是直接引用 0.9815。

4.6 结论

  1. 分辨率是本任务的第一要素，其影响远超骨干容量与超参调节；
  2. 集成不是万能的 —— 只有当成员"同样强、且犯错的地方不一样"时才有增益；
  3. 阈值标定必须建立在正确的误差分析之上 —— 我们一度差点把 58 张"模型判断错误" 当成"阈值过严"去调参，那会白费功夫且指标下降；
  4. 剩余错误的性质已经变了：从"模型能力不足"变成"任务设计的固有难度" （近似款 hard_negative），继续提升需要专门的训练策略。

5. 智能体设计

5.1 DeepSeek 接入方式

项目 值
接口 https://api.deepseek.com/chat/completions（OpenAI 兼容）
模型 deepseek-v4-flash（任务书规定）
认证 Authorization: Bearer <API_KEY>，Key 只从环境变量或 agent/.env.local 读取
关键参数 messages / tools / tool_choice / temperature / max_tokens

为什么用原生 Function Calling 而不是"让模型输出 JSON 再解析"：

原生 文本解析
参数格式 API 保证合法 JSON 要处理代码块、多行、转义
并行调用 tool_calls 数组天然支持 要自定义协议
结束判定 finish_reason 明确 靠猜测
稳定性 高 换个写法就崩

实测发现的两个细节：

  1. reasoning_content（思维链）会计入 completion_tokens —— 一次"只回复两个字"的请求实测消耗 133~218 token，所以 max_tokens 不能设太小；
  2. finish_reason == "length" 必须当成可补救的错误处理 —— 我们为它单列错误码 OUTPUT_TRUNCATED，并自动放大 max_tokens 重试一次。

5.2 工具定义

共 12 个工具，每个都带 JSON Schema 与写给模型看的 description：

# 工具 作用
1 classify_car 调用自训练视觉模型识别图片中的车型
2 query_car_info 查车型资料（品牌/车身/简介/看点/档次）
3 list_supported_cars 列出支持的车型
4 save_car_trims 把联网查到的档次/价格存进档案库（必须带来源）
5 compare_car_trims 比出各档次之间真正有差别的参数
6 add_car_record 记入个人看车档案（可记"看中的是哪一档"）
7 search_my_records 检索个人档案
8 update_record_note 修改备注
9 delete_car_record 删除记录
10 my_garage_stats 档案统计
11 web_search 搜索公网信息（需开启联网）
12 browse_page 用真实浏览器打开网页读取内容（需开启联网）

工具定义示例：

{
  "type": "function",
  "function": {
    "name": "classify_car",
    "description": "识别图片中的车型。当用户上传/提供车辆图片时调用。返回 Top-K 候选与置信度；置信度低于阈值时返回 unknown…",
    "parameters": {
      "type": "object",
      "properties": { "top_k": {"type": "integer", "minimum": 1, "maximum": 10} },
      "additionalProperties": false
    }
  }
}

两个设计要点：

  1. description 本身就是提示词。写得含糊，模型就不知道何时调、参数怎么填。 所以每个工具的 description 都写清了：用途、何时调用、边界、失败处理；
  2. 把工具从清单里拿掉，比在工具里拒绝更有效。没开联网时， web_search / browse_page 根本不放进 tools 数组 —— 模型看不见就不会调。

5.3 连续工具调用流程

主循环（agent/loop.py）：

1. 组装系统提示词（分节 + 运行时上下文）
2. 调模型
3. 没有 tool_calls → 结束，返回回复
4. 有 tool_calls → 逐个执行 → 结果回填 → 回第 2 步

工具执行流水线（7 步），参考主流 agent harness 的做法：

1. 查表      name → ToolDefinition        未注册 → UNKNOWN_TOOL
2. 解析参数  JSON 字符串 → dict            解析失败 → INVALID_ARGUMENTS
3. 校验参数  JSON Schema（自研校验器）      不合规 → INVALID_ARGUMENTS
4. 前置门禁  pre_execute 钩子              拒绝 → DENIED_BY_POLICY
5. 执行主体  带超时、带取消信号             超时 → TOOL_TIMEOUT
6. 后置处理  post_execute 钩子             可替换/补充结果
7. 记账      写 JSONL 工具调用记录

防无限循环的四道机制（都是实战逼出来的）：

机制 实现 解决什么
轮数预算 max_rounds=12 硬上限
预算警告 剩余 ≤2 时注入 <budget_warning> 提前提醒模型收敛
预算耗尽兜底 最后一次不给工具，逼模型基于已有信息作答 避免"抓到资料却回 0 字"
重复调用短路 相同工具+参数的指纹 → 复用结果（标 _cached） 联网工具昂贵

真实事故：早期预算 8 轮 / 16 次调用时，一次联网问答模型搜了 6 次、开了 10 个页面， 最后 MAX_ROUNDS_EXCEEDED、回复 0 字。后来加到 12/24 并补齐了后三条。

一次真实的多轮工具链（实测日志）：

用户 > 帮我看看这张图是什么车，顺便查查它有什么配置版本、大概多少钱

  ↳ classify_car(image)           → 日产_轩逸 (0975) 置信度 0.98
  ↳ query_car_info(0975)          → 品牌/车身/简介；档次库为空
  ↳ web_search("轩逸 配置 价格")   → 找到汽车之家配置页、报价页

                row_keywords=["天窗","座椅","中控","辅助驾驶"])  → 抓到档次表
  ↳ browse_page(报价页)            → 指导价 7.99-17.49 万

助手 > 轩逸共 18 个配置版本，指导价 7.99-17.49 万…

5.4 Session 与低置信度处理

Session：append-only 事件日志（JSONL）是唯一事实来源

{"ts":"…","type":"user_message","payload":{"text":"这是什么车？","image":"…"}}
{"ts":"…","type":"tool_call","payload":{"tool":"classify_car","arguments":{…}}}
{"ts":"…","type":"tool_result","payload":{"tool":"classify_car","ok":true,"result":{…}}}
{"ts":"…","type":"assistant_message","payload":{"message":{…},"final":true}}

为什么用事件日志： ① 可重放 —— 切换会话时按事件重放，能还原完整对话（含工具卡片）； ② 可审计 —— 每个动作都有时间戳；③ 抗崩溃 —— append + flush + fsync； ④ 可派生 —— 会话标题、轮数、联网开关状态全都从事件推导。

低置信度处理：两个阈值，管两件事

阈值 含义 处理
拒识 0.20 最高概率太低 → 不认了 输出 unknown，如实告知
提示 0.70 给出车型但把握不大 展示 Top-K 候选 + 建议重拍

0.70 来自选择性预测分析：在验证集上找"准确率 ≥ 98.5% 所需的置信度门槛"。 0.20 < 0.70，逻辑分层：先判断是否拒识，再看要不要提示。

第一层：稳定的错误码体系（28 个）

工具调度  UNKNOWN_TOOL / INVALID_ARGUMENTS / DENIED_BY_POLICY / TOOL_TIMEOUT / TOOL_FAILED / ABORTED
视觉业务  IMAGE_NOT_FOUND / IMAGE_UNREADABLE / MODEL_NOT_LOADED
档案业务  CAR_NOT_FOUND / RECORD_NOT_FOUND / UNKNOWN_CAR
模型网络  API_KEY_MISSING / API_REQUEST_FAILED / API_RESPONSE_INVALID / MODEL_REFUSED
          OUTPUT_TRUNCATED / MAX_ROUNDS_EXCEEDED
网络分层  NETWORK_DNS_FAILED / NETWORK_UNREACHABLE / NETWORK_TLS_FAILED
          API_TIMEOUT / API_RATE_LIMITED / API_SERVER_ERROR

第二层：把底层异常翻译成人话

用户原本看到的是：

ConnectionError: HTTPSConnectionPool(host='api.deepseek.com', port=443):
Max retries exceeded ... NameResolutionError ... getaddrinfo failed

既看不出坏在哪一层，也看不出"这不是你代码的问题"。所以我们做了网络分层诊断：

① DNS 解析     api.deepseek.com → 112.49.40.58, 183.253.56.58 · 10 ms
② TCP 443      3 个 IP 逐个测：2 个通（6~8ms），1 个黑洞（TimeoutError）
③ TLS 握手     TLSv1.3 · 55 ms
④ HTTPS 可达   GET → HTTP 401（未带 Key，正常）

第三层：区分"值得重试"与"快速失败"

指数退避 + ±25% 抖动（防止多个会话同时重试造成惊群）。 DNS 抖动 / 429 / 5xx 值得重试；401 / 403（Key 错了）快速失败，重试 100 次也没用。

8.2 存在的不足

① 没有独立测试集，泛化能力只能估计

教师只提供了 train/val，我们所有选择（阈值、模型、TTA 档位、集成组合）都基于同一个验证集。 我们主动做了两层交叉验证来量化乐观偏差（tools/verify_generalization.py）， 结果是 −0.0003（5 折标定交叉验证）和 −0.0003（含模型选择的完全诚实流程）， 说明过拟合很轻微。但这仍不等价于一个真正没参与过任何选择的独立测试集 —— 教师提供测试集后应当用它做最终确认。

另外，验证集只有 2422 张，交叉验证显示单次评估的噪声约 ±0.006 —— 这意味着讨论 0.001~0.002 量级的差异时要谨慎，我们报告的所有"增益"都远大于这个噪声。

② 剩余错误已触及任务设计的天花板

61 张错误里 unknown 占 25 张，这些是刻意挑选的 hard_negative （如 MINI CLUBMAN 考你能否和 MINI 区分）。继续提升需要专门针对近似款的训练策略 （难例挖掘、对比学习），不是调参能解决的。

③ 联网抓取受站点结构影响

browse_page 的表格抽取针对汽车之家的配置页结构优化过。 换站点（懂车帝、易车）需要重新调选择器 —— 目前是"能用但不通用"。

④ 拒识机制比较朴素

用的是"max softmax 概率 + 全局阈值"。学术界有更好的 OOD 检测方法 （Energy-based、Mahalanobis 距离、专门训练的二分类器）。我们选了最简单可解释的方案。

⑤ 没有移动端

目前是 Web 界面，实际"路边拍车"场景更适合手机 App。

8.4 项目收获

技术层面：掌握了从数据处理、模型训练、阈值标定到智能体编排、Web 系统、 测试体系的完整链路，而不只是"调个 API"。

方法层面 —— 三条比技术更重要的：

  1. 测量优于猜测。 训练慢，我第一反应是"GPU 不行"，实际是数据管道（GPU 有 79% 时间在等数据）； 分数上不去，我以为是"模型不够好"，实际是分辨率看不清。 每次老老实实分段计时/分档统计，都比猜得快。
  2. 不要相信"看起来该有用"的方法。 这次试了四种提升手段，四个"理论上可行"的全部失败 （多尺度 TTA、快照集成、调阈值、弱模型集成）， 真正有效的是最朴素的"让模型看得更清"。
  3. 不报错的 bug 最难查。 缓存不看权重、标定口径不一致 —— 这类问题不会崩、不会报错， 只是"结果莫名不对"。关键指标必须人工复核，不能只看流程跑没跑通。
