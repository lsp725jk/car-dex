19 · 技术全景与关系图谱

这篇不是"技术清单"，而是技术之间的关系网。

一篇清单能告诉你"用了什么"，但回答不了真正重要的问题： 为什么用它？它和别的技术什么关系？什么时候有用、什么时候没用？可以换成什么？

每一节都尽量给出：它解决什么问题 → 依赖谁 → 可被谁替代 → 和谁互补 → 和谁冲突 → 实测效果。

配套：13 · 技术栈全解（版本与用法的字典）· 18 · 进阶训练技术（训练技术深入）· 15 · 微调实战指南

第 0 章 · 怎么读这篇

0.1 五种关系

技术之间的关系只有五种，认清了就能自己推导出该用什么：

关系 符号 含义 例子
依赖 A → B A 要工作必须先有 B PyTorch → CUDA（想用 GPU 就得有 CUDA 版 torch）
替代 A ‖ B A 和 B 解决同一问题，二选一 SSE ‖ WebSocket（都是服务端推送）
互补 A + B 一起用效果更好 数据增强 + EMA + 标签平滑
冲突 A ✗ B 不能同时用 / 一起用会变差 MixUp ✗ SupCon；强增强 ✗ 微调
前置 A ⊳ B 必须先做 A 才能做 B 训练 ⊳ 标定阈值 ⊳ 用拒识

0.2 三条判断原则

① 先问"瓶颈在哪"，再问"用什么技术"。

本项目最典型的例子：分数卡在 0.96 时，我的第一反应是"换更大的模型"。 实际测量后发现，79% 的时间 GPU 在等数据、错误集中在"看不清"而不是"不够聪明" —— 真正的瓶颈是数据管道和分辨率，跟模型容量无关。

② 优先试"零成本"和"低成本"的技术。

零成本      后处理、阈值标定、模型选择
低成本      TTA（零训练，推理 ×N）、集成已有模型
中成本      超参/分辨率重训（几十分钟 GPU）
高成本      损失函数改造、换架构（改代码 + 大量调试）

③ 分数越高，每种方法的边际收益越小。

阶段 方法选对的收益
0.85 → 0.95 一次能涨 0.05~0.10
0.95 → 0.98 一次能涨 0.002~0.005
0.98 以上 所有方法加起来只涨 0.003

第 2 章 · 分层解析

2.1 语言与运行时层

技术 作用 依赖 可替代 什么时候用
Python 3.13 全部后端、训练、推理 — Julia / C++ 生态最全，AI 领域事实标准
JavaScript (ES2020+) 前端交互 浏览器 TypeScript / 框架 想零构建就原生
HTML5 / CSS3 页面结构与样式 — — 无替代
SQL 关系型查询 SQLite ORM 查询简单、数据结构化时
PowerShell 5.1 一键启动 Windows bash Windows 上的自动化
Batch 双击入口 cmd — 只做"挑一个 PowerShell"

关系：

  • PowerShell → Python：脚本负责找解释器、查 Key、跑自检，然后启动 Python 服务
  • Batch → PowerShell：.bat 内容全 ASCII（不受编码影响），只负责挑选 pwsh/powershell
  • Python ‖ JavaScript：不是替代关系，是分工 —— Python 做重活，JS 只做展示

为什么不用 TypeScript / React：这个项目要交给老师、要能在别人机器上跑起来。 "双击就能跑"的价值远大于"用了某某框架"。1587 行原生 JS 实现了侧边栏、 设置面板、SSE 流式、工具卡片、主题切换 —— 功能不缺。

2.2 数值与图像层

技术 作用 依赖 可替代 什么时候用
NumPy 数组运算、概率计算 — 纯 Python 一切数值计算的地基
Pillow (PIL) 图像读取、格式校验、变换 — OpenCV 简单 I/O 与预处理
pandas 表格统计 NumPy 纯 Python 数据分析脚本
scikit-learn 指标计算（F1/混淆矩阵） NumPy 自实现 评估层，不参与训练
matplotlib 训练曲线、错误样本可视化 NumPy plotly 出图

关系：

Pillow → NumPy → PyTorch          （图像 → 数组 → 张量）
PyTorch → NumPy → scikit-learn    （张量 → 数组 → 指标）

关键认识：scikit-learn 只在评估层，不参与训练。 它算 Macro-F1、混淆矩阵、分类报告 —— 这些是"打分"用的，和模型本身无关。

为什么不用 OpenCV：项目只需要读图、缩放、裁剪、色彩抖动， 这些 Pillow + torchvision.transforms 已经覆盖，且和 PyTorch 的数据管道无缝衔接。 引入 OpenCV 只会多一个依赖。

2.3 深度学习层（核心）

这是最厚的一层，先看骨架，再看训练技术。

2.3.1 框架骨架

技术 作用 依赖 关系
PyTorch 张量、自动求导、优化器、DataLoader NumPy 地基
torchvision 模型工厂 + 预训练权重 + 图像变换 PyTorch → PyTorch
CUDA 12.6 runtime GPU 加速 NVIDIA 驱动 → PyTorch
cuDNN 卷积的 GPU 实现 CUDA → PyTorch
bfloat16 / float16 混合精度 CUDA（fp16）/ CPU（bf16） + PyTorch

关系链：

NVIDIA 驱动 ⊳ CUDA runtime ⊳ cuDNN ⊳ PyTorch(CUDA 版) ⊳ 训练
                                       ↓
                          如果装的是 CPU-only 构建 → 全链条失效

踩过的坑：机器上有 RTX 4060，但 torch 装的是 +cpu 构建 —— torch.cuda.is_available() 只看编译时有没有链接 CUDA，跟驱动和显卡无关。 而且 pip install torch==2.13.0 换不掉，因为 PEP 440 规定 ==2.13.0 会匹配上 2.13.0+cpu，必须写 torch==2.13.0+cu126。

2.3.2 模型架构

架构 参数量 作用 实测（同 288）
ResNet18 11.2 M 轻量基线 —
ResNet50 23.6 M 主力 0.9779
Wide ResNet50_2 66.9 M 大容量 0.9798

关系：

  • ResNet18 → ResNet50 → Wide ResNet50_2：容量递增，但收益递减
  • 18→50：参数量 ×2.1，精度 +0.0082
  • 50→Wide：参数量 ×2.8，精度 +0.0019
  • 参数量 ‖ 分辨率：两者都能提升精度，但分辨率更划算
  • ResNet50 288→416（参数不变）：+0.0036
  • 换大 2.8 倍参数：+0.0019

结论：如果图上本来就没有足够信息，再大的模型也学不出区分能力。 调参顺序：先拉分辨率，再考虑换模型。

2.3.3 训练技术全景（最重要的一节）

这一节的核心：这些技术不是并列的，它们分属五个不同的目的。 搞清楚"我要解决什么问题"，才能选中对的技术。

目的 技术 解决的问题
A. 让模型看得清 分辨率 ↑ 细粒度特征像素不够
B. 让模型学得稳 迁移学习 · 优化器 · 调度器 · 混合精度 训练不收敛/太慢
C. 让模型不过拟合 数据增强 · 标签平滑 · EMA · MixUp/CutMix · Dropout 小数据上死记硬背
D. 让模型更会分 对比学习(SupCon) · 类别权重 近似款分不开
E. 让模型答得准 TTA · 集成 · 阈值标定 推理时榨出最后一点

A. 让模型看得清

技术 作用 依赖 冲突 实测
分辨率 224→288→352→416 增加输入信息量 — — +0.0187 / +0.0027 / +0.0009

关键约束：训练分辨率必须等于推理分辨率。 224 训的模型拿到 288 推理会掉点（0.9597 → 0.9509），因为物体表观尺寸变了、 感受野对应的物理尺度也变了。

B. 让模型学得稳

技术 作用 依赖 替代 实测
迁移学习（ImageNet 权重） 不用从零学通用特征 torchvision 从头训 是 0.85 → 0.95 的主因
SGD + Momentum 参数更新 — AdamW 迁移学习上泛化更好
余弦退火 + 线性预热 学习率调度 — Step / OneCycle 平滑收敛；预热防初期震荡
混合精度（fp16/bf16） 加速 + 省显存 CUDA / CPU fp32 CPU 上 1.5×
梯度裁剪 防梯度爆炸 — — 与 clip=5.0
cudnn.benchmark 自动选最快卷积算法 CUDA — 输入尺寸固定时有效

关系： * 优化器 + 调度器 是一对，不能只看优化器 * 混合精度 → 需要 CUDA（fp16）或 支持 AVX512-BF16 的 CPU（bf16） * 梯度裁剪 + 混合精度 互补：半精度更容易数值异常，裁剪是保险

踩过的坑：head_lr_mult=10 配 lr=0.01 → 训崩（val_loss 2889、Macro-F1 0.007）。 分类头是随机初始化的，学习率再 ×10 = 0.1，一步就推飞了。

C. 让模型不过拟合

技术 作用 依赖 冲突 实测/说明
RandomResizedCrop 位置/尺度不变性 — — 与 eval Resize+CenterCrop 配对
水平翻转 左右不变性 — — 车左右近似对称，几乎无副作用
ColorJitter 光照/白平衡不变性 — — hue 只给 0.08（大了会把白车变绿车）
RandAugment 自动增强（选 N 个操作 + 固定强度） — ✗ 微调 主实验用 (2, 7)
RandomErasing 模拟遮挡 必须在 ToTensor 之后 ✗ 微调 p=0.25
标签平滑 0.1 抑制过度自信 — — 对拒识有帮助
权重 EMA 0.999 平滑训练噪声 — — 保存的是 EMA 权重
MixUp 样本线性混合 — ✗ SupCon α=0.2
CutMix 区域粘贴混合 — ✗ SupCon α=0.5
Dropout 随机丢弃 分类头 — 本项目未启用

三组重要关系：

  1. 数据增强 + 标签平滑 + EMA + MixUp 是互补的，它们从不同角度防过拟合： 增强改变输入分布、标签平滑改变目标分布、EMA 平滑参数轨迹、MixUp 改变样本组合。 本项目把这四个一起用，是 0.85 → 0.95 的主要来源。

  2. 强增强 ✗ 微调：微调时模型已经学得不错， 再上 RandAugment 会让它退步。所以微调用 moderate_train，关掉 RandAugment/Erasing， label_smoothing 从 0.1 降到 0.05。

  3. MixUp/CutMix ✗ SupCon：混合样本的标签是软标签（两类概率的线性组合）， 而 SupCon 需要硬标签判断谁是正样本。

D. 让模型更会分

技术 作用 依赖 替代 实测
迁移学习 用通用特征起步 torchvision — 基础
类别权重（逆频率） 处理不平衡 — 先验校正 τ 实测不如先验校正
对比学习 SupCon 特征空间拉开同类异类距离 双视图 + 投影头 + fine 标签 三元组损失 单独 +0.0002，集成 +0.0010
微调（fine-tune） 在已训好的模型上继续学 — 从头训 见第 15 篇

类别权重 ‖ 先验校正 τ —— 这是本项目一个重要的"二选一"判断：

两者都在处理"训练集类别不平衡"，但方式不同：

类别权重：  改训练过程 —— 加权后的损失函数让模型在训练时就偏向少数类
先验校正 τ： 改推理过程 —— z' = z − τ·log(π)，直接在 logit 上拉回偏置

本项目选了后者，理由：可标定、可验证、不影响模型本身。 实测在更好的模型上，类别权重反而让 Macro-F1 下降。

一般原则：能在推理侧解决的问题，不要放到训练侧。 推理侧可以扫描、可以回滚、不改变模型；训练侧是"一次性"的，改错了要重训。

对比学习的四个前提（缺一不可）：

SupCon → 需要正样本对        → 双视图（因为 51 类 batch 32 凑不出同类）
SupCon → 需要硬标签          → 关闭 MixUp
SupCon → 需要"同类"定义正确   → fine 标签（不能用 51 类标签！）
SupCon → 需要防表示崩塌      → 投影头

第 3 条是本项目最关键的设计决策： unknown 是 98 个车系的混合体。对 51 类标签做 SupCon 会把所有 unknown 拉成一团 —— 等于让 MINI CLUBMAN 和卡车变相似，有害。 用 fine 标签（50 已知 + 98 来源 = 149 类）才对 —— 而来源标签就藏在文件名里。

E. 让模型答得准

技术 作用 依赖 冲突 实测
TTA·水平翻转 2 视角平均 — — 基础
TTA·多裁剪 10 视角平均（中心+四角 × 翻转） 训练分辨率 ✗ 多尺度 +0.0025
TTA·多尺度 换分辨率推理 — ✗ 训练/测试不匹配 只 +0.0005
模型集成·等权平均 多模型 log-softmax 几何平均 成员同样强 ✗ 弱成员 +0.0009 ~ +0.0016
先验校正 τ 修正类别偏置 训练集类别频率 — 与阈值联合扫描
拒识阈值 t 低于阈值判 unknown 需标定 — 见下
快照集成 同一次训练多个 epoch — ✗ 相关性太高 −0.0017

三条关键认识：

  1. 多裁剪 ‖ 多尺度（名字像，效果相反） 多尺度改分辨率（模型没见过的尺度 → 掉点）；多裁剪保持分辨率只换裁剪位置。 区分车型的关键部位（格栅、大灯）不一定在画面正中央。

  2. 弱成员 ✗ 集成 —— 等权平均里，弱成员是负资产。 0.9752 + 0.9507 的组合（0.9719）比强者单独还差。 集成要的是"同样强、但犯错的地方不一样"。

  3. 阈值标定有前提：必须先有训练好的模型，才能扫 (τ, t)。 而且更换 TTA 档位后必须重新标定 —— 多视角平均会压平概率分布 （实测同一张图置信度从 0.979 → 0.629），最优阈值从 0.30 降到 0.20。

技术 作用 依赖 可替代

关系：

  • SSE ‖ WebSocket：需求是服务器单向推送 → 选 SSE。它就是 text/event-stream + data: <json>\n\n，纯文本、易调试、浏览器自动重连。
  • threading ⊳ SSE：Flask 生成器是同步的，Agent 也是同步的， 但要"边跑边推" → 后台线程跑 Agent + 主线程轮询队列：
queue = []
def on_event(ev): queue.append(ev)          # Agent 回调，在工具线程里被调用
th = threading.Thread(target=worker); th.start()
while not done or sent < len(queue):        # 主线程轮询并 yield
    while sent < len(queue):
        yield sse(queue[sent]); sent += 1
    time.sleep(0.05)

为什么不用 Celery/Redis：课设规模不需要，引入只增加部署复杂度。 Flask threaded=True + 会话级锁就够。

第 7 章 · 常见误区

误区 1："有显卡就能用 GPU"

真相：torch.cuda.is_available() 只看编译时有没有链接 CUDA。 装的是 +cpu 构建时，有卡也是 False。而且 pip install torch==2.13.0 换不掉 （PEP 440：==2.13.0 匹配 2.13.0+cpu），必须写 torch==2.13.0+cu126。

误区 2："训练慢就是模型太大"

真相：实测 GPU 有 79% 的时间在等数据（num_workers=0）。 数据增强在 CPU 上做，串行跑就把 GPU 饿死了。先量再优化。

误区 3："集成一定比单模型好"

真相：等权平均里弱成员是负资产。 0.9752 + 0.9507 → 0.9719，比强者单独还差。 集成要的是"同样强、但犯错的地方不一样"。

误区 4："AUROC 高就是方法好"

真相：AUROC 只衡量排序质量，最终指标还依赖阈值落点。 Energy 的 AUROC 高了 0.029，Macro-F1 反而低 0.001。

误区 5："换个更强的损失函数就能涨分"

真相：SupCon 单独只 +0.0002。 方法的理论增益只有在"误差确实来自那个缺陷"时才能兑现。 分数高的时候，剩余误差多半是任务固有难度。

误区 6："缓存能加速，加上就行"

真相：缓存键必须包含被缓存内容的全部输入。 本项目的 finalize.py 缓存只按 run 名索引 → 重训后静默复用旧结果， 指标一字不差却没更新，而且不报任何错。

误区 7："实验代码和生产代码可以各写各的"

真相：标定用的推理口径必须和上线时逐字节一致。 实验脚本 0.9815、生产代码 0.9695，差 0.012 —— 因为两组视角的加权方式不同。 对策：写 reproduce_production.py，用生产代码跑一遍验证集对比。

误区 6 和 7 的共同特征：不崩、不报错，只是"结果莫名不对"。 这类 bug 最难查 —— 所以关键指标必须人工复核，不能只看流程跑没跑通。

第 9 章 · 一句话总览

如果只记十条：

  1. 先诊断，再选方法 —— 误差分析比试方法重要
  2. 先试零成本的 —— TTA、阈值标定、模型选择
  3. 分辨率 > 容量 —— "看不清"永远比"不够聪明"更致命
  4. 训练和推理的分辨率必须一致 —— 多尺度推理是无效的
  5. 集成成员要同样强 —— 弱成员是负资产
  6. 能在推理侧解决的，不要放到训练侧 —— 可标定、可回滚
  7. 缓存键必须含全部输入 —— 否则会出现"不报错的错"
  8. 标定口径必须等于生产口径 —— 否则指标是假的
  9. 分数越高，边际收益越小 —— 判断依据是"剩余错误是什么性质"
  10. 关键指标要人工复核 —— 流程跑通 ≠ 结果正确
