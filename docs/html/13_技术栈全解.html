3.2 模型架构

骨干网络（src/cardex/models.py）：

分类头改造（迁移学习的关键一步）：

model = factory(weights=weights if pretrained else None)   # 加载 ImageNet 预训练
in_features = model.fc.in_features                         # ResNet18: 512, ResNet50: 2048
if dropout > 0:
    model.fc = nn.Sequential(nn.Dropout(p=dropout), nn.Linear(in_features, num_classes))
else:
    model.fc = nn.Linear(in_features, num_classes)         # 51 类输出

即：换掉最后的全连接层，输出从 ImageNet 的 1000 类变成 51 类（50 款车型 + 1 个 unknown）。

参数分组（param_groups）：可以给分类头单独设置学习率倍数（head_lr_mult）。 本项目最终用 1.0（不分开放），因为早期用 10 + lr=0.01 直接训崩了 —— val_loss 飙到 2889、Macro-F1 只有 0.007。

3.3 数据增强（torchvision.transforms）

项目实现了 4 档变换策略，按强度递增：

档位 组成 用在
eval Resize(256, BILINEAR) → CenterCrop(224) → ToTensor → Normalize 验证 / 推理
baseline_train RandomResizedCrop + RandomHorizontalFlip(0.5) 实验 A
moderate_train 上面 + ColorJitter + RandomErasing 实验 B
strong_train 上面 + RandAugment + RandomRotation 实验 C1/C2（最终方案）

逐个技术点：

  • RandomResizedCrop(224, scale=(0.50, 1.0)) —— 随机位置裁剪 + 缩放。 scale 下限 0.5 意味着最狠只裁到原图的 50%，保证车里还有足够信息。
  • RandomHorizontalFlip(p=0.5) —— 水平翻转。车是左右近似对称的，这个增强几乎无副作用。
  • ColorJitter(brightness/contrast/saturation=0.35, hue=0.08) —— 模拟不同光照与白平衡。hue 只给 0.08，因为色相变化过大会把白车变绿车，反而不合理。
  • RandAugment(num_ops=2, magnitude=7) —— Google 在 2019 年提出的自动增强： 从一组操作里随机选 N 个、以固定强度 M 施加（不需要像 AutoAugment 那样搜策略）。 这里"选 2 个、强度 7"是精度/成本的折中。
  • RandomErasing(p=0.25) —— 随机抹掉一块区域（模拟遮挡 / 车牌挡住车身）。 它必须放在 ToTensor 之后，因为操作对象是张量。
  • RandomRotation(degrees) —— 小角度旋转，模拟拍摄角度。
  • Normalize(IMAGENET_MEAN, IMAGENET_STD) —— 用 ImageNet 的均值方差归一化。 这是和预训练权重配套的：用了 ImageNet 权重就必须用同一套归一化参数， 否则特征分布对不上，精度会明显下降。
  • InterpolationMode.BILINEAR —— 双线性插值缩放，比最近邻平滑。

3.4 训练技巧（src/cardex/engine.py）

① 优化器：SGD + Momentum + Weight Decay

torch.optim.SGD(params, lr=0.01, momentum=0.9, weight_decay=1e-4)

选 SGD 而不是 Adam 的原因：迁移学习场景下 SGD+动量 泛化通常更好， 且超参在 ResNet 系列上非常成熟（lr=0.01, momentum=0.9, wd=1e-4 是经典组合）。

② 学习率调度：线性预热 + 余弦退火

def lr_lambda(step):
    if step < warmup_steps:                      # 预热：从 0 线性升到 1 倍
        return (step + 1) / warmup_steps
    prog = (step - warmup_steps) / (total_steps - warmup_steps)
    return 0.5 * (1 + cos(pi * prog))            # 余弦：1 → 0 平滑下降
scheduler = torch.optim.lr_scheduler.LambdaLR(optimizer, lr_lambda)
  • 预热 2 个 epoch：一开始参数是随机的，直接大学习率容易震荡甚至发散。
  • 余弦退火：比阶梯下降平滑，末段学习率趋近 0，让模型"稳稳落进"极小值。
  • 调度是按 step（而不是按 epoch）计算的，粒度更细。

③ CPU bfloat16 混合精度

with torch.autocast("cpu", dtype=torch.bfloat16, enabled=amp):
    outputs = model(images)
loss = criterion(outputs.float(), targets)       # 损失在 float32 里算
  • bfloat16 有和 float32 一样的 8 位指数范围，不容易溢出（fp16 就常溢出）。
  • 实测 CPU 上约 1.5 倍加速。
  • 损失必须在 float32 里算，否则数值精度不够会导致 loss 不下降。
  • ⚠️ 踩过的坑：bf16 与 fp32 推理会有 0.0005 的指标漂移。 解决方式是评估脚本默认沿用 checkpoint 里记录的 amp 设置，保证训练/评估一致。

④ 混合样本增强：MixUp + CutMix

images, soft_targets = mixup_cutmix_batch(images, targets,
                                          mixup_alpha=0.2, cutmix_alpha=0.5, prob=0.35)
loss = soft_cross_entropy(outputs, soft_targets)
  • MixUp：两张图按比例线性叠加（x = λx₁ + (1-λ)x₂），标签同样混合。
  • CutMix：把一张图的一块矩形区域贴到另一张图上，标签按面积比例混合。
  • prob=0.35：只有 35% 的 batch 做混合 —— 全用会拖慢收敛。
  • 因为标签变成了"软标签"（概率分布），交叉熵也要相应改成 soft cross entropy。

⑤ 标签平滑（Label Smoothing）

loss = soft_cross_entropy(logits, targets, smoothing=0.1)

把 one-hot 的 [0,0,1,0] 变成 [0.025,0.025,0.925,0.025]。 作用是抑制过度自信，提升泛化 —— 对我们的"拒识"能力也有帮助。

⑥ 权重 EMA（指数滑动平均）

ema_state = decay * ema_state + (1 - decay) * param      # decay=0.999

保存 checkpoint 时存的是 EMA 权重而不是原始权重。 EMA 相当于对训练轨迹做平均，能显著平滑掉噪声、提升验证精度。

⑦ 梯度裁剪

torch.nn.utils.clip_grad_norm_(model.parameters(), 5.0)   # 梯度范数上限

防止偶发的梯度爆炸把参数打飞。

⑧ optimizer.zero_grad(set_to_none=True)

把梯度置为 None 而不是 0，省一次内存写入，是 PyTorch 官方推荐的写法。

⑨ 类别不平衡

训练集最多类 2.33 倍于最少类。项目试过 class_weight="inverse"（逆频率加权） 与 unknown_weight_mult（unknown 类额外加权），并在实验 B 验证过。 最终方案没有用类别权重 —— 因为实验发现先验校正 τ 已经能处理， 而加权反而让 Macro-F1 下降。

3.5 推理侧技术

① TTA（Test-Time Augmentation，测试时增强）

logits = (log_softmax(model(x)) + log_softmax(model(flip(x)))) / 2

推理时把原图与水平翻转图各跑一遍，在 log 概率空间取平均。 代价是推理时间翻倍，换约 +0.3~0.5 个点。

注意是 log_softmax 求平均（几何平均），不是 softmax 求平均（算术平均）。 前者对概率差异更敏感，集成效果通常更好。

② 多模型集成（Soft Voting / 几何平均）

for member, w in zip(members, weights):
    logits = log_softmax(member(x)) - tau * log_prior     # 先做先验校正
    acc += logits * (w / sum(weights))                    # 加权求和
probs = softmax(acc)                                      # 再转回概率

最终方案是 ResNet18@224 + ResNet50@224 两模型集成，验证集 Macro-F1 从 单模型的 0.9510 / 0.9592 提升到 0.9604。

③ 先验校正（Prior Adjustment，τ）

logits = logits - tau * log(pi)      # pi = 训练集类别频率

训练集类别不平衡会让模型偏向高频类。减去 τ·log(π) 就是把这种偏向拉回来。 τ=0.05 由验证集扫描确定。

④ 拒识阈值（Rejection Threshold，t）

idx = where(max_prob < t, UNKNOWN_INDEX, argmax)

最大概率低于 t=0.25 就判为 unknown。这是让模型"知道自己不知道"的机制， 也是任务书 5.5 节要求的核心。

⑤ 阈值必须来自验证集

src/calibrate.py 在验证集上做 (τ, t) 二维网格扫描， 按 Macro-F1 选最优点。绝不能拍脑袋定阈值 —— 拍脑袋的阈值在新数据上必然失效。

3.6 评估指标

src/cardex/metrics.py，底层用 scikit-learn：

指标 sklearn 调用 说明
Macro-F1 f1_score(y, ŷ, average="macro", zero_division=0) 本项目的评分标准：51 类等权平均 F1
Accuracy accuracy_score 整体正确率
每类 P/R/F1 precision_recall_fscore_support 定位哪一类弱

为什么 Macro-F1 而不是 Accuracy：本项目的 51 类样本量差异大（最多类 2.33 倍）， Accuracy 会被大类主导；Macro-F1 让每一类同等重要，更能反映"是不是每一款车都认得出来"。

Top-K 混淆对分析（top_confusions）：从混淆矩阵里挑出最容易被搞混的类对， 例如"奥迪A6 与 奥迪A6L"，为错误分析提供依据。

5.1 DeepSeek 开放平台 API

项目 值

响应结构（本项目实测）：

{
  "choices": [{
    "message": {
      "role": "assistant",
      "content": "",                      // 最终文本
      "reasoning_content": "…",           // 思维链（本模型有！）
      "tool_calls": [{ "id": "...", "type": "function",
                       "function": { "name": "...", "arguments": "{…}" } }]
    },
    "finish_reason": "stop" | "tool_calls" | "length"

两个实测发现：

  1. reasoning_content 会占用 completion_tokens。 一次"只回复两个字"的请求消耗 133~218 token。所以 max_tokens 不能设太小， 否则思维链还没写完就被截断（finish_reason: "length"）。
  2. finish_reason == "length" 必须当成一种可补救的错误。 本项目为它单列了错误码 OUTPUT_TRUNCATED，并自动放大 max_tokens 重试一次。

5.2 Function Calling（工具调用）

这是整个任务二的技术核心。链路是：

用户消息 → 模型返回 tool_calls（工具名 + JSON 参数）
        → 我们执行工具，把结果作为 role="tool" 消息回填
        → 模型基于结果继续推理，或再调工具，或给出最终回答

工具定义格式（OpenAI 风格）：

{
  "type": "function",
  "function": {
    "name": "classify_car",
    "description": "识别图片中的车型…（模型靠这段描述决定何时调用）",
    "parameters": {
      "type": "object",
      "properties": { "top_k": {"type": "integer", "minimum": 1, "maximum": 10} },
      "required": [],
      "additionalProperties": false
    }
  }
}

description 是提示词的一部分。写得含糊，模型就不知道该不该调、参数怎么填。 本项目每个工具的 description 都写清了：用途、何时调用、边界、以及"查不到要如实报错"。

5.3 Agent Loop（智能体主循环）

agent/loop.py 的 Agent.run_turn() 是最核心的一段代码。每一轮：

1. 组装系统提示词（分节 + 运行时上下文）
2. system + 历史消息  → 调模型
3. 如果模型没给 tool_calls  → 本轮结束，返回回复
4. 如果有 tool_calls → 逐个执行 → 结果回填 → 回到第 1 步

围绕这个循环的工程机制（这些才是"能上生产"和"玩具"的区别）：

机制 实现 解决的问题
轮数预算 max_rounds=12 防止模型无限循环
工具次数预算 max_tool_calls=24 防止一次请求打爆 API
预算警告 剩余 ≤2 时注入 <budget_warning> 系统消息 提醒模型"别再查了，作答"
预算耗尽兜底 最后一次不给工具，逼模型基于已有信息作答 避免"抓到一堆资料却回 0 字"
熔断 同一工具连续 3 次相同失败 → 中止 防止原地打转
重复调用短路 相同工具+参数指纹 → 复用上次结果（标 _cached） 联网工具只读且昂贵
结果截断 超 6000 字做结构化裁剪（保 JSON 合法） 防上下文爆炸
网络重试 指数退避 + ±25% 抖动 DNS 抖动 / 限流 / 5xx
截断补救 OUTPUT_TRUNCATED → 放大 max_tokens 重试 大参数对象写不下
事件流 on_event 回调，实时推送

5.4 工具执行流水线

参考主流 agent harness（Codex / Claude Code）的做法，把"执行一次工具"拆成 7 步 （agent/tools/registry.py）：

1. 查表      name → ToolDefinition          未注册 → UNKNOWN_TOOL
2. 解析参数  JSON 字符串 → dict              解析失败 → INVALID_ARGUMENTS
3. 校验参数  JSON Schema                    不合规 → INVALID_ARGUMENTS
4. 前置门禁  pre_execute 钩子                拒绝 → DENIED_BY_POLICY
5. 执行主体  带超时、带取消信号               超时 → TOOL_TIMEOUT

5.5 自研 JSON Schema 校验器

agent/schema.py，零依赖实现（不引入 jsonschema 包）。支持的关键字：

5.8 会话与事件日志

agent/session.py。核心设计：append-only 事件日志（JSONL）是唯一事实来源。

{"ts":"2026-09-15 23:20:11","type":"session_meta","payload":{...}}
{"ts":"...","type":"user_message","payload":{"text":"这是什么车？","image":"..."}}
{"ts":"...","type":"turn_context","payload":{"turn_id":"t-…","tools":[...]}}
{"ts":"...","type":"tool_call","payload":{"tool":"classify_car","arguments":{...}}}
{"ts":"...","type":"tool_result","payload":{"tool":"classify_car","ok":true,"result":{...}}}
{"ts":"...","type":"assistant_message","payload":{"message":{...},"final":true}}
{"ts":"...","type":"turn_end","payload":{"ok":true,"rounds":4,"tools_used":[...]}}

为什么用事件日志而不是直接存消息列表：

  • 可重放：切换会话时按事件重放就能还原整段对话（含工具卡片）；
  • 可审计：每个动作都有时间戳，出问题能查；
  • 抗崩溃：append + flush + fsync，进程被杀也读得到最后一条；
  • 可派生：会话标题、轮数、联网开关状态全都能从事件里推导，不用另存字段。

每条事件都会 os.fsync() —— 这有点慢，但换来的是"断电也不丢已发生的操作"。

5.9 离线替身（ScriptedClient）

ScriptedClient 是 DeepSeekClient 的测试替身：没有 API Key 时， 它用规则模拟模型的工具调用决策，驱动完全同一套 Agent Loop。

class DeepSeekClient:      # 真实：HTTP 调 DeepSeek
    def complete(self, messages, tools=None, tool_choice="auto", notify=None): ...
class ScriptedClient:      # 替身：按规则返回 tool_calls / 文本
    def complete(self, messages, tools=None, tool_choice="auto", notify=None): ...

它的价值： * 无 Key / 断网时仍能演示完整工具链； * 让"智能体骨架"的自查结果可复现（真实模型有随机性）。

它的边界：替身只走固定分支，发现不了真实模型才会触发的缺陷。 本项目的经验是：接真实 Key 跑一遍，才挖出 4 个离线测不出来的 bug。

6.2 SSE（Server-Sent Events）

对话接口用 SSE 而不是 WebSocket，因为只需要服务器单向推送，SSE 更简单。

协议格式（就是纯文本，每条消息 data: <json>\n\n）：

def sse(event: dict) -> str:
    return f"data: {json.dumps(event, ensure_ascii=False, default=str)}\n\n"

同步函数 → 生成器的桥接（Flask 的生成器是同步的，而 Agent 也是同步的， 但需要边跑边推）：

queue = []
def on_event(ev):          # Agent 的回调，被工具执行线程调用
    queue.append(ev)

th = threading.Thread(target=worker)      # 后台线程跑 run_turn
th.start()
while not done or sent < len(queue):      # 主线程轮询队列并 yield
    while sent < len(queue):
        yield sse(queue[sent]); sent += 1
    time.sleep(0.05)

事件类型：session / turn_start / model_request / tool_call / tool_result / assistant_message / api_retry / api_recovered / budget_final / error / result。

8. 浏览器自动化：Chrome DevTools Protocol

这是"查实时价格"这条链路的关键技术，也是最"硬核"的一块。

8.1 为什么需要真浏览器

懂车帝、汽车之家这类站点是前端渲染的：requests 抓回来的 HTML 是个空壳， 数据要等 JS 跑完才有。实测对比「汽车之家 轩逸页」：

方式 结果
requests 抓 HTML 只有导航骨架，一条价格都没有
真实浏览器渲染后取正文 2018 字，含 厂商指导价：7.99-17.49万、经销商报价 6.39-14.19万

8.2 为什么不用 Playwright / Selenium

  • Playwright：要装 Python 包 + 下载浏览器（~150 MB）；本机虽然缓存了 Chromium，但版本对不上。
  • Selenium：要装包 + 驱动，且 API 更啰嗦。

CDP 是浏览器自带的调试协议，用 WebSocket 直连就能操控 —— 只需要 websocket-client（很多环境已有），零额外依赖、不下载任何东西。

8.3 协议关键点（三个必踩的坑）

坑 1：不能直连 page 级 WebSocket。 Chrome 111+ 起，直接连 /devtools/page/<id> 的 WS 会被服务端关闭。 正确姿势是连 browser 级 WS，然后用 flat session：

Target.createTarget({url})           → targetId
Target.attachToTarget({targetId, flatten:true}) → sessionId
之后所有命令带 sessionId 字段

坑 2：Origin 校验。 浏览器会拒绝带 Origin 头的 WS 握手，返回 403： Rejected an incoming WebSocket connection from ...。 两面都要处理：客户端 suppress_origin=True，服务端加 --remote-allow-origins=*。

坑 3：选哪个可执行文件。 优先用 chrome-headless-shell —— 它不拉 GPU 进程，最省资源也最稳。 实测用完整的 chrome.exe --headless=new 会在受限环境里因 mojo 命名管道被拒而崩。 候选顺序：环境变量 CARDEX_BROWSER → Playwright 缓存 → 系统 Chrome → 系统 Edge。

10.1 网络分层诊断

tools/selfcheck.py --net 把"能不能连上"拆成四层，坏在哪层就停在哪层：

① DNS 解析     api.deepseek.com → 112.49.40.58, 183.253.56.58 · 10 ms
② TCP 443      3 个 IP 逐个测：2 个通（6~8ms），1 个黑洞（TimeoutError）
③ TLS 握手     TLSv1.3 · 55 ms
④ HTTPS 可达   GET https://api.deepseek.com → HTTP 401（未带 Key，属正常）

为什么要逐个 IP 测：api.deepseek.com 挂在 CDN 后面，一次解析返回多个 A 记录。 实测出现过"3 个 IP 里 1 个黑洞、另外 2 个 6ms" —— 只测第一个会给出误导性结论。

10.2 错误分类（把底层异常翻译成人话）

classify_request_error() 按网络栈自下而上判定：

判据 错误码 可重试
NameResolutionError / getaddrinfo failed / [Errno 11001] NETWORK_DNS_FAILED ✅
SSLError / certificate verify failed NETWORK_TLS_FAILED ❌（配置问题）
ProxyError NETWORK_UNREACHABLE ✅
Timeout API_TIMEOUT ✅
HTTP 429 API_RATE_LIMITED ✅
HTTP 5xx API_SERVER_ERROR ✅
HTTP 400/401/402/403 API_REQUEST_FAILED ❌（快速失败）

为什么要做这个：用户原本看到的是这样一坨：

ConnectionError: HTTPSConnectionPool(host='api.deepseek.com', port=443):
Max retries exceeded ... NameResolutionError ... getaddrinfo failed

既看不出坏在哪一层，也看不出"这不是你代码的问题"。

10.3 重试策略

wait = min(retry_backoff * (2 ** (attempt - 1)), 8.0)   # 指数退避：0.8 / 1.6 / 3.2
wait *= 0.75 + random.random() * 0.5                     # ±25% 抖动

抖动（jitter）的作用：多个会话同时失败时，纯指数退避会让它们同时重试， 形成"惊群"。加随机抖动能把重试时间打散。

几个值得学的测试思想：

  1. 把测试分层：不依赖模型的那层（工具层）用确定性断言；依赖模型的那层放宽措辞、 只断言行为（调了哪些工具、状态对不对）。
  2. 离线替身保证可复现：骨架自查默认走 ScriptedClient，结果每次都一样。
  3. 同一个 bug 要能被测出来：修 MAX_ROUNDS_EXCEEDED 后专门加了压力测试。
  4. 测试不能破坏数据：verify_trims.py 冷启动前会备份，跑完再合并回去。
  5. 反复跑：很多 bug（进程泄漏、重复累积、偶发失败）只有重复运行才暴露。

# 教训
1 离线替身测试通过 ≠ 真实链路没问题 —— 接真 Key 后挖出 4 个离线测不出的 bug
2 数据越多越容易踩的坑：工具结果超长被截断成非法 JSON，把整轮对话打断
3 "看不见"比"调了再拒绝"更好：没权限的工具就别放进模型清单
4 模型会一直搜集到撞墙：必须有预算警告 + 强制作答兜底
5 中文名字不能按字符相似度判重：舒适版/舒享版 相似度 0.93 却是两款车
6 价格是比名字更可靠的判据
7 拿不准就不要合并：多一条重复只是烦，错误合并会丢数据
8 原始异常字符串不是给用户看的：要把 "getaddrinfo failed" 翻译成"DNS 挂了，这么办"
9 字符集和编码是 Windows 上的头号坑：.ps1 要 BOM、日志要 encoding='utf-8'
10 反复跑：进程泄漏、数据累积、偶发失败，跑一遍永远发现不了
