# 一、数据与选题

## Q1. 827 类里为什么选这 50 类？给个可检验的标准。

**为什么问**：这是最容易"拍脑袋"的地方。老师想看你是不是有据可依。

**回答**：六条原则，写成代码在 `src/select_classes.py` 里，不是手工挑的：

| 原则 | 内容 |
| --- | --- |
| **P1 主题契合** | 只选私人用户会"看、比、记"的乘用车与轻型商用车型，排除重卡/牵引车等工程车辆 |
| **P2 车身类型覆盖** | 轿车 / SUV / MPV / 跑车 / 微面 / 轻客 六类都有代表 |
| **P3 品牌多样性** | 覆盖 **37 个品牌**；同品牌最多 2 类，且车身形态差异明显（奔驰 E 级轿车 vs GLE SUV） |
| **P4 单车系单一代表** | 同一车系的衍生版（探岳 / 探岳X / 探岳GTE）**只取一个** |
| **P5 样本充足** | 训练样本 ≥ 80 张、验证样本 ≥ 26 张 |
| **P6 造型辨识度** | 优先选设计语言差异大的（方盒子越野、超跑、微型电动车） |

最终分布：**SUV 21 / 轿车 17 / MPV 4 / 跑车 4 / 微面 2 / 轻客 2**。

> **P4 是 Macro-F1 的关键**。评分是 51 类等权平均，把"探岳"和"探岳X"都选进来，
> 这两类会互相吃掉对方的 F1 —— 相当于人为给分数设了个天花板。

**追问"为什么不超过 50 类"**：任务书规定 `classes.txt` 必须**恰好 50 行**。

## Q2. unknown 是怎么构造的？会不会有数据泄漏？

**为什么问**：unknown 构造是这类拒识任务**最容易出错**的地方，也是最能体现严谨性的地方。

**回答**：三条硬约束，全部写进 `configs/unknown_sources.json` 可追溯：

```
来源类别    98 个（34 个同品牌兄弟车型 + 64 个其他品牌）
train 采样  每类 20 张 → 1960 张
val  采样   每类  6 张 →  588 张
```

1. **来源类别与 50 类完全不重叠** —— 脚本里有断言校验；
2. **train / val 样本不重复** —— train 从来源类别的**训练**图片取，val 从来源类别的**验证**图片取；
3. **完全不使用测试图片** —— 教师没提供测试集，我们也没拿任何未来数据。

**33% 的 unknown 是刻意挑的"近似款"**（`source_kind: hard_negative`）。例如：

```jsonc
{ "id": "0702", "name": "MINI_MINI CLUBMAN",
  "source_kind": "hard_negative", "target_class_id": "0264" }   // 0264 = MINI_MINI
```

**这不是随便选的**：MINI CLUBMAN 和 MINI 外观极像，就是要考模型能否**分辨"像但不同"**。

**追问"这不公平吧，太像了"**：恰恰相反 —— 如果 unknown 全是卡车、飞机，模型闭着眼都能拒识，
那这个指标就没有意义了。**拒识能力必须用"近似款"来测。**

实测数据支持这个设计有效：hard_negative 的误拒率 **12.7%**，
是其他品牌 unknown（2.9%）的 **4.4 倍** —— 说明这部分确实是难点，也确实被区分开了。

## Q3. 数据泄漏查了吗？

**回答**：查了三项，写进 `outputs/reports/data_analysis.txt`：

| 检查项 | 结果 |
| --- | --- |
| 完全重复图片（MD5 相同） | 1 组，涉及 2 张 —— **其中跨 train/val 重复 0 组** |
| 类内近重复（dHash 汉明距离 ≤ 5） | **0.00%** |
| train/val 文件名集合交集 | 空 |

**跨 train/val 的 MD5 重复是 0** —— 这是最要命的一类泄漏（同一张图既训又测），
如果有，指标会虚高。同一划分内的那 1 组重复无害。

## Q4. 为什么 train 7494 张、val 2422 张，而不是把 827 类全用上？

**回答**：三个理由。

1. **选题定位**是"私人车型资料库"，不是"识别所有车"。50 类已经能覆盖 6 种车身形态和 37 个品牌；
2. **unknown 需要有意义的来源**：正因为我们**没用**其他 777 类，它们才成了天然的 unknown 来源。
   如果全用上，就没有 unknown 了；
3. **算力与时间**：CPU-only 环境下训练一组实验要 1.5~3 小时。50 类是我们能做完
   "5 组对照实验 + 完整消融 + 阈值标定"的规模。

# 二、模型与训练

## Q5. 预训练权重从哪来？是官方 ImageNet 权重吗？

**为什么问**：任务书明确要求"不得使用现成汽车分类模型或第三方在线识别接口"。

**回答**：**只用 torchvision 官方 ImageNet 预训练权重**，代码里写死成常量并注明版本：

```python
SUPPORTED = {
    "resnet18":          (models.resnet18,          models.ResNet18_Weights.IMAGENET1K_V1),
    "resnet50":          (models.resnet50,          models.ResNet50_Weights.IMAGENET1K_V1),
    "wide_resnet50_2":   (models.wide_resnet50_2,   models.Wide_ResNet50_2_Weights.IMAGENET1K_V2),
}
```

* **没有**下载任何汽车专用模型；
* **没有**调用任何在线图片识别 API；
* ImageNet 的 1000 类里**不含任何具体车型**，是通用特征。

**追问"V1 还是 V2"**：这里踩过坑。ResNet50 的 V2 权重文件是 `resnet50-11ad3fa6.pth`，
本机缓存里只有 V1（`0676ba61`）。写错版本会触发联网下载并失败，所以**把版本钉死**。

## Q6. 5 组对照实验分别想说明什么？

**回答**：每一组只改一个变量，用来**归因**。

| 实验 | 改了什么 | 标定后 Macro-F1 | 结论 |
| --- | --- | --- | --- |
| `baseline_resnet18_160` | ResNet18 @160，基础增强 | 0.8512 | 基线 |
| `weighted_resnet18_160` | + 逆频率类别权重 | 0.8597 | 类别加权有小幅收益 |
| `improved_resnet18_224` | @224 + 强增强 + 标签平滑 + MixUp/CutMix + EMA + TTA | 0.9510 | **分辨率与增强是主因** |
| `improved_resnet50_224` | 换 ResNet50 | 0.9592 | 骨干容量 +0.008 |
| **`r50_288` / `r50_352`** | 提高到 288 / 352 | **0.9752 / 0.9781** | **分辨率是最大杠杆** |

**从 0.8512 到 0.9815，最大的单步增益来自提高分辨率（+0.030）**，不是换更大的骨干。

---

## Q7. 为什么最终没用类别权重？明明数据不平衡。

**为什么问**：这是个经典陷阱 —— 教科书说"不平衡就加权"，但我们实测**没用**。

**回答**：**因为实测反倒更差**。

* 训练集不平衡比 2.33（最多类 186 张 vs 最少类 80 张），确实不平衡；
* 我们在实验 B（`weighted_resnet18_160`）里试了 `class_weight="inverse"`，F1 从 0.8512 → 0.8597，**看似有提升**；
* **但在更优的模型上，先验校正 τ 已经能处理这件事**，而且更干净：
  `z' = z − τ·log(π)` 直接在 logit 上做校正，不需要动训练过程；
* 实测在 `improved_resnet18_224` 上，最优 τ = +0.10 就已经把类别偏置拉回来了。

**结论**：**类别加权和先验校正是"同一件事的两种做法"，不要叠加。** 我们选了后者 —— 它可标定、可验证、不影响模型本身。

---

## Q8. 阈值是怎么定的？为什么是 0.20 而不是 0.5？

**为什么问**：阈值是拒识的核心，拍脑袋定必然翻车。

**回答**：**在验证集上做二维网格扫描**（`src/calibrate.py` / `src/finalize.py`）：

```
τ ∈ [−0.4, +0.6]  步长 0.1      （先验校正强度）
t ∈ [0.00, 0.60]  步长 0.05     （拒识阈值）
按 51 类 Macro-F1 选最优点
```

**为什么不是 0.5**：0.5 是"二分类的直觉"，但这里有两件事让它不适用：

1. **模型是 51 类 softmax**，概率被摊到 51 个类上，峰值天然低于二分类；
2. **多视角 TTA 会把分布压平** —— 实测同一张图，单视角置信度 0.9854、多裁剪后只有 0.6291。

所以最优阈值实测在 **0.20~0.30** 区间。而且**换 TTA 档位必须重新标定**：
从 hflip 换成多裁剪，最优 t 从 0.30 降到 0.20，沿用旧值会大量误拒。

## Q9. 为什么用 `head_lr_mult=1.0` 而不是 10？

**回答**：**因为 10 训崩了**。这是真实事故：

```
lr=0.01, head_lr_mult=10
→ val_loss 飙到 2889，Macro-F1 只有 0.007
```

分类头是新初始化的，学习率再乘 10 = 0.1，一步就把随机初始化的头推飞了。

后来改成 `head_lr_mult=1.0`（不分开放）就稳了。**这个教训直接指导了后面的微调设计** ——
微调时按模式给不同学习率（head 模式 1e-3、full 模式 5e-5，相差 20 倍），
核心原则是"改动越多的部分、学习率越小"。

# 三、指标与评估

## Q10. 为什么用 Macro-F1 而不是 Accuracy？

**回答**：任务书规定的评分口径，而且理由充分：

* 51 类**样本量差异大**（unknown 588 张 vs 最少的类 26 张）；
* Accuracy 会被大类主导 —— unknown 一类就占验证集 **24%**；
* **Macro-F1 让每一类等权**，更能反映"是不是每一款车都认得出来"。

**一个直观证据**：某个模型的 Accuracy 0.9674，看着很高；但 Macro-F1 只有 0.9752 里的差距
说明**弱类被大类掩盖了**。我们逐类看 F1，最低的类（如日产_轩逸 0.925）就是优化重点。

---

## Q11. Macro-F1 是怎么算的？unknown 算不算进去？

**回答**：**算**。评分是 **51 类**等权 Macro-F1 —— 50 个车型 + 1 个 unknown。

```python
f1_score(y_true, y_pred, labels=list(range(51)), average="macro", zero_division=0)
```

* `labels=range(51)` 显式指定，**即使某类在预测里一次都没出现，也占 1/51 的权重**；
* `zero_division=0` —— 该类的 F1 记 0，而不是忽略。

**这一点很重要**：如果一个模型把所有 unknown 都硬认成某个车型，
unknown 类的 F1 = 0，直接损失 1/51 ≈ 0.0196。

## Q12. `predictions.csv` 里 unknown 的 `predicted_label` 写什么？

**回答**：写 **`unknown`** 这个字符串。

```csv
image_id,predicted_label,confidence
```

因为它是一个合法的输出标签（索引 50），不是"缺失值"。

# 四、结果可信度（**最关键的一组**）

## Q13. 0.9815 是在验证集上挑出来的，凭什么相信测试集也是这个水平？

**为什么问**：**这是最致命的问题**。我们在验证集上做了大量选择（扫阈值、
比 6 种集成组合、试 3 种 TTA 档位），验证集分数必然偏乐观。

**回答**：我们**主动做了交叉验证来量化这个偏差**，而不是回避。
结论是 **−0.0003** —— 差距几乎为零。

做法（`tools/verify_generalization.py`）：把验证集分 5 折，
**在 4 折上扫 τ/t，在留出折上评估** —— 这模拟"用一批新数据标定、拿到另一批新数据上用"。

```
折 1: 标定集 1937 张 → τ=+0.1 t=0.20  →  留出折 485 张 → 0.9801
折 2:                                  →  留出折 485 张 → 0.9818
折 3:                                  →  留出折 484 张 → 0.9897
折 4:                                  →  留出折 484 张 → 0.9713
折 5:                                  →  留出折 484 张 → 0.9834

留出折平均 = 0.9812 ± 0.0059
与报出的 0.9815 的差距 = −0.0003
```

**更严格的一层**：每一折不仅重扫 τ/t，还在 4 种配置（TTA 档位 × 集成组合）里
**重新挑冠军**，再看它在留出折上的表现：

```
折 1~5 全部选中「288+352@多裁剪」→ 平均 0.9812 ± 0.0059，差距 −0.0003
```

**5 折全部选中同一个配置** —— 说明我们的选择流程是稳健的，
不是"试了很多组合碰运气碰上的"。

**追问"±0.0059 是什么"**：那是**抽样噪声**，不是模型不稳定。
每折只有约 484 张，样本量小所以波动大；平均值与全集结果几乎完全一致就是证据。
它同时告诉我们一个重要事实：**验证集只有 2422 张，单次评估的精度极限约 ±0.006** ——
所以讨论 0.001~0.002 量级的差异要谨慎。我们报告的所有增益（+0.0025 以上）都远大于这个噪声。

**追问"这能替代测试集吗"**：**不能**。这给出的是"如果换一批同分布的新数据能拿到多少"的估计，
仍不等价于一个真正没参与过任何选择的独立测试集。
教师提供测试集后应当用它做最终确认，而不是直接引用 0.9815。**这一点我们写进了报告。**

## Q13b. 换个拍照条件还行吗？鲁棒性怎么样？

**回答**：测了 7 种扰动（606 张子集）：

| 扰动 | 相对原图 | 判断 |
| --- | --- | --- |
| JPEG 质量 30 | **−0.0013** | ✅ 几乎无影响 |
| 亮度 ×0.6 | −0.0022 | ✅ |
| 亮度 ×1.5 | −0.0042 | ✅ |
| 旋转 10° | −0.0063 | ✅ |
| 高斯模糊（半径 2） | **−0.0672** | ⚠️ 明显下降 |
| **低分辨率（短边 96px）** | **−0.4988** | ❌ **灾难性下降** |

**三条结论：**

1. **对常见拍摄差异很鲁棒** —— 压缩、曝光、轻微手抖的影响都在 0.007 以内，
   印证了数据增强（ColorJitter、随机裁剪）确实学出了尺度/亮度不变性；
2. **对模糊敏感** —— 真实场景的"运动抓拍""没对上焦"会掉 0.067，是改进方向；
3. **对分辨率极度敏感** —— 96px 直接掉到 **0.49**。
   **这反向印证了本项目最重要的结论：分辨率是第一要素。**
   **实践建议**：客户端应拒绝过小的图片或提示重拍。

## Q14. 20% 的验证集是 unknown，这个比例合理吗？

**回答**：**偏高，但这是有意的设计选择，而且我们在报告里说明了。**

* 真实场景中"不在 50 款库里"的车占比取决于用户 —— 一个私人看车用户，
  拍到陌生车的概率**不低**；
* 24% 的 unknown 比例让拒识能力**被充分评估**，而不是被 50 个已知类淹没；
* **代价要说清楚**：如果真实场景 unknown 只占 5%，那么 unknown 类在 Macro-F1 里的
  权重仍是 1/51（Macro-F1 等权），所以**指标不受比例影响** —— 这是 Macro-F1 相对 Accuracy 的又一个好处。

---

## Q15. 训练集和验证集的划分是谁做的？会不会有偏？

**回答**：**是教师按约 1:3 划分的，我们没动**。

我们验证过划分的一致性：各类的 `val/train` 比例在 **0.325 ~ 0.333** 之间，
均值 0.331 —— 说明划分是**按类分层**的，不是随机的。

**我们额外做的事**：把 unknown 的 train/val 也按同样的逻辑分开
（来源类别的训练图 → unknown 训练集；来源类别的验证图 → unknown 验证集），
保证 unknown 内部也不泄漏。

## Q16. GPU 训练和 CPU 训练结果不一样，说明什么？

**回答**：说明**换设备只影响快慢，不影响质量**，但**会影响随机性**。

| | CPU | GPU |
| --- | --- | --- |
| C1 | 0.9510 | 0.9507 |
| C2 | 0.9592 | 0.9597 |
| 集成 | 0.9604 | 0.9625 |

同一个 `seed=42`，两次结果不完全一样 —— 因为 **cuDNN 在 GPU 上会挑不同的卷积算法**，
浮点运算顺序变了，结果就有微小差异。这是**正常的非确定性**，不是 bug。

**结论**：差异量级（±0.001）远小于我们的改进幅度（+0.017），所以不影响结论。

# 五、智能体设计

## Q17. DeepSeek 是怎么接入的？为什么用 Function Calling 而不是自己解析文本？

**回答**：用 **OpenAI 兼容的 `/chat/completions` + `tools` 参数**（原生 Function Calling）。

**为什么不用"让模型输出 JSON 再正则解析"**：

| | 原生 Function Calling | 文本解析 |
| --- | --- | --- |
| 参数格式 | API 保证是合法 JSON | 要处理 markdown 代码块、多行、转义 |
| 并行调用 | `tool_calls` 是数组，天然支持 | 要自己定协议 |
| 调用终止 | `finish_reason` 明确区分 `stop` / `tool_calls` | 要靠猜测 |
| 稳定性 | 高 | 模型换个写法就崩 |

实测遇到的**唯一**相关坑是 `finish_reason: "length"`（输出被 `max_tokens` 截断），
我们给它单列了错误码 `OUTPUT_TRUNCATED` 并自动放大预算重试。

## Q18. 工具是怎么定义的？模型怎么知道该调哪个？

**回答**：标准 JSON Schema + **一段写给模型看的 `description`**：

```json
{
  "type": "function",
  "function": {
    "name": "classify_car",
    "description": "识别图片中的车型。当用户上传/提供车辆图片时调用…（含边界与失败处理说明）",
    "parameters": {
      "type": "object",
      "properties": { "top_k": {"type": "integer", "minimum": 1, "maximum": 10} },
      "additionalProperties": false
    }
  }
}
```

**关键认识**：`description` **本身就是提示词的一部分**。写得含糊，模型就不知道
该不该调、参数怎么填。所以每个工具的 description 都写清了：用途、何时调用、边界、
以及"查不到要如实报错"。

**还有一个容易忽略的点：把工具从清单里拿掉，比在工具里拒绝更有效。**
没开联网时，`web_search` / `browse_page` **根本不放进 tools 数组** ——
模型看不见就不会调，比"调了再返回 DENIED"体验好得多。

## Q19. "连续工具调用"具体怎么实现的？怎么防止无限循环？

**回答**：循环是 `agent/loop.py` 的 `run_turn()`：

```
1. 组装系统提示词（分节 + 运行时上下文）
2. 调模型
3. 没有 tool_calls → 结束，返回回复
4. 有 tool_calls → 逐个执行 → 结果回填 → 回第 2 步
```

**四道防循环机制**（都是实战逼出来的）：

| 机制 | 实现 | 解决什么 |
| --- | --- | --- |
| 轮数预算 | `max_rounds=12` | 硬上限 |
| 预算警告 | 剩余 ≤2 时注入 `<budget_warning>` 要求立即作答 | 提前提醒 |
| **预算耗尽兜底** | 最后一次**不给工具**，逼模型基于已有信息作答 | 避免"抓到资料却回 0 字" |
| 重复调用短路 | 相同工具+参数的指纹 → 复用上次结果（标 `_cached`） | 联网工具只读且昂贵 |

**真实事故**：早期预算 8 轮 / 16 次调用时，一次联网问答模型搜了 6 次、开了 10 个页面，
最后 `MAX_ROUNDS_EXCEEDED`，**回复 0 字**。后来加到 12/24，并补了上面后三条。

## Q20. Session 是怎么做的？为什么用事件日志？

**回答**：**append-only 事件日志（JSONL）是唯一事实来源**。

```jsonl
{"ts":"…","type":"user_message","payload":{"text":"这是什么车？","image":"…"}}
{"ts":"…","type":"tool_call","payload":{"tool":"classify_car","arguments":{…}}}
{"ts":"…","type":"tool_result","payload":{"tool":"classify_car","ok":true,"result":{…}}}
{"ts":"…","type":"assistant_message","payload":{"message":{…},"final":true}}
```

**为什么不用"直接存消息列表"**：

* **可重放** —— 切换会话时按事件重放，能还原完整对话（含工具卡片）；
* **可审计** —— 每个动作都有时间戳；
* **抗崩溃** —— `append + flush + fsync`，进程被杀也读得到最后一条；
* **可派生** —— 会话标题、轮数、联网开关状态全都从事件推导，不用另存字段。

实测这个设计救过一次：`truncate` 把 JSON 截断成非法格式时，`_parse_for_log()`
保证日志仍可读，整个会话不会因为一条坏记录而损坏。

## Q21. 低置信度怎么处理？和拒识有什么区别？

**为什么问**：这两个概念很容易混。

**回答**：**两个阈值，管两件事**：

| | 阈值 | 含义 | 处理方式 |
| --- | --- | --- | --- |
| **拒识** `unknown_threshold` | **0.20** | 最高概率太低 → **不认了** | 输出 `unknown`，如实告知"不在资料库里" |
| **提示** `display_confidence_threshold` | **0.70** | 给出了具体车型，但**把握不大** | 仍输出车型，但**展示 Top-K 候选 + 建议重拍** |

**为什么要有第二个**：只做拒识的话，模型要么"很确定"要么"拒答"，中间地带体验很差。
0.70 这个值来自选择性预测分析（`tools/derive_confidence_threshold.py`）——
在验证集上找"准确率 ≥ 98.5%"所需的置信度门槛。

**追问"这两个值会不会冲突"**：不会。0.20 < 0.70，所以逻辑是分层的：
先看是否拒识，再看不拒识的情况下要不要提示。

## Q22. 怎么防止模型编造数据？特别是价格。

**为什么问**：这是大模型最危险的地方，而且价格编得特别像真的。

**回答**：**三道防线**（专门为档次/价格数据设计）：

1. **来源必填** —— `save_car_trims` 的 `source_url` 是必填参数，不合法直接 `INVALID_ARGUMENTS`，
   没有来源的数据根本进不了库；
2. **来源核验** —— 扫描本会话事件日志，检查该 URL 是否**真的用 `browse_page` 打开过**。
   没打开过的标 `verified: false`，并把"本会话真正打开过的 URL 列表"回给模型让它改正；
3. **界面展示** —— 每条数据带来源站点、抓取时间、核验状态，用户一眼看到出处。

**实测效果**（问一款从没查过的车）：

> 宝马 X7 在车型库里（宝马 · 大型 SUV，ID 0222），但**档案库里还没有它的档次和价格数据** ——
> 教师数据集本来就不含价格，这块得联网去查。……训练数据里的车价早就过期了，
> **我编一个数只会误导你**。

# 六、Web 与工程

## Q23. API Key 是怎么管理的？会不会泄露？

**回答**：三重保护。

1. **只存环境变量或 `agent/.env.local`**，该文件在 `.gitignore` 里；
2. **接口不回传明文** —— `GET /api/settings` 的响应里**根本没有 `api_key` 字段**，
   前端密码框是"只写不读"；
3. **不落盘到配置** —— `runtime_config.json` 只存可调参数，自查脚本里有断言检查
   "该文件不含 `sk-`"。

代码、报告、截图里一律只出现掩码 `sk-f…fbe5（长度 35）`。

## Q24. SSE 和 WebSocket 选哪个？为什么？

**回答**：选 **SSE**。因为需求是**服务器单向推送**（把 Agent 的执行过程推给前端），
不需要双向。SSE 更简单：

* 就是 `text/event-stream` + `data: <json>\n\n`，纯文本，容易调试；
* 自动重连（浏览器内置）；
* 不需要额外的握手协议。

**实现上的一个细节**：Flask 的生成器是同步的，Agent 也是同步的，
但需要"边跑边推"。桥接方式是**后台线程跑 Agent + 主线程轮询队列**：

```python
queue = []
def on_event(ev): queue.append(ev)      # Agent 的回调，在工具线程里被调用
th = threading.Thread(target=worker); th.start()
while not done or sent < len(queue):    # 主线程轮询并 yield
    while sent < len(queue):
        yield sse(queue[sent]); sent += 1
    time.sleep(0.05)
```

## Q25. 异常处理是怎么做的？

**回答**：分三层。

**第一层：稳定的错误码体系（28 个）**

```
工具调度  UNKNOWN_TOOL / INVALID_ARGUMENTS / DENIED_BY_POLICY / TOOL_TIMEOUT / TOOL_FAILED
视觉业务  IMAGE_NOT_FOUND / IMAGE_UNREADABLE / MODEL_NOT_LOADED
档案业务  CAR_NOT_FOUND / RECORD_NOT_FOUND / UNKNOWN_CAR
模型网络  API_KEY_MISSING / API_REQUEST_FAILED / API_RESPONSE_INVALID / OUTPUT_TRUNCATED
网络分层  NETWORK_DNS_FAILED / NETWORK_UNREACHABLE / NETWORK_TLS_FAILED / API_TIMEOUT / …
```

**第二层：把底层异常翻译成人话**

用户原本看到的是：

```
ConnectionError: HTTPSConnectionPool(host='api.deepseek.com', port=443):
Max retries exceeded ... NameResolutionError ... getaddrinfo failed
```

既看不出坏在哪一层，也看不出"这不是你代码的问题"。所以我们做了**网络分层诊断**：

```
① DNS 解析     api.deepseek.com → 112.49.40.58, 183.253.56.58 · 10 ms
② TCP 443      3 个 IP 逐个测：2 个通（6~8ms），1 个黑洞（TimeoutError）
③ TLS 握手     TLSv1.3 · 55 ms
④ HTTPS 可达   GET → HTTP 401（未带 Key，正常）
```

**第三层：可自愈的失败要自动重试**

指数退避 + ±25% 抖动（防止多个会话同时重试造成惊群）。
并且区分"值得重试"（DNS 抖动、429、5xx）和"快速失败"（401、403 —— Key 错了重试 100 次也没用）。

## Q26. 为什么不用 Celery / Redis / 前端框架？

**回答**：**因为 50 类的课设规模不需要，引入只会增加部署复杂度。**

* **并发**：Flask `threaded=True` + 会话级锁就够。Agent 对同一会话加锁，不同会话可并发；
* **前端**：原生 JS + CSS 变量，没有 npm、没有构建工具，**双击就能跑**。
  实测代码量 1587 行，功能完整（侧边栏、设置面板、SSE 流式、工具卡片、主题切换）；
* **判据**：一个要交给老师看、要能在他机器上跑起来的项目，**"零依赖启动"的价值**远大于
  "用了某某框架"。

# 七、测试

## Q27. 怎么保证代码是对的？测了多少？

**回答**：**六个自查套件，共 299 项**，全部可复现：

| 套件 | 项数 | 测什么 |
| --- | --- | --- |
| `src/verify_submission.py` | 41 | 任务一交付物合规（`classes.txt` 恰好 50 行 4 位升序、`predictions.csv` 2422 条） |
| `tools/selfcheck.py` | 41 | 环境、依赖、权重、端口、**网络分层诊断**、真实 API + 视觉实测 |
| `tools/verify_agent.py` | 118 | 骨架自查，**离线可复现**，逐条对照任务书第五、六节 |
| `tools/e2e_test.py` | 61 | A 段工具层（20，不走模型）+ B 段真实模型（41，10 个场景） |
| `tools/verify_browser.py` | 21 | 真实浏览器抓取链路 |
| `tools/verify_trims.py` | 17 | 档次知识库全链路 + 反编造 |

**关键设计：测试要分层。**

* 不依赖模型的那层用**确定性断言**（工具层，结果必须一模一样）；
* 依赖模型的那层**只断言行为**（调了哪些工具、状态对不对），措辞放宽；
* 骨架自查默认走 `ScriptedClient`（离线替身），**保证结果可复现**。

## Q28. 测出来的 bug，举几个最有代表性的。

**回答**：挑了五个，每个都写进了报告。

**BUG-1：Top-K 里混进了 `unknown` 行**
`predict_batch` 忽略了 `top_k` 参数，而且返回的 Top-K 包含 unknown 那一条。
修法：过滤掉 unknown，且请求 `top_k+1` 条再截断。

**BUG-2：工具结果被截断成非法 JSON，把整轮对话打断**
`truncate()` 在 3000 字符处硬切，正好切在 JSON 字符串中间，
后面的 `json.loads` 抛 `JSONDecodeError`。**触发概率约 1/8**。
修法：`truncate_tool_result()` 做**结构化裁剪**（保 JSON 合法）+ `_parse_for_log()` 永不抛异常。

**BUG-3：`MAX_ROUNDS_EXCEEDED` 时回复 0 字**
明明已经抓到一堆资料，却因为"轮数用完了"一个字都不给用户。
修法：预算耗尽前**先要一次「不带工具的最终回答」**，逼模型基于已有信息作答。

**BUG-4：`finalize.py` 缓存不看权重**（最隐蔽）
缓存文件名只按 run 名拼，**重训之后照样读旧缓存** ——
指标、排名、`predictions.csv` 全是旧模型的，**而且不报任何错**。
发现方式：GPU 重训完跑 finalize，数字和 CPU 版**一字不差**，一眼看出不对劲。
修法：缓存键里加 checkpoint 指纹（大小 + mtime 的 MD5）。

**BUG-5：标定口径和生产推理口径不一致**
实验脚本算出 0.9815，生产代码复现只有 **0.9695**，差 0.012。
根因是两组 TTA 视角的加权方式不同（实验 50/50 vs 生产 2/7）。
修法：统一口径，并写 `tools/reproduce_production.py` 专门做这个对比。

> **教训**：**缓存键必须包含被缓存内容的全部输入**；
> **标定用的推理口径必须和上线时逐字节一致**。
> 这类 bug 的共同点是**不报错**，只是"结果莫名不对"。

## Q29. 怎么证明测试不是在"自说自话"？

**回答**：三个措施。

1. **用真实模型 + 真实浏览器跑**，不是 mock。`tools/verify_trims.py` 会真的去
   汽车之家抓配置表、真的调 DeepSeek 存进档案库；
2. **测试会真的失败**。299 项里我们见过各种失败 —— 而且每次失败都能定位到具体代码。
   如果测试从来不过，或者改什么都过，那它就没价值；
3. **反复跑**。很多 bug（进程泄漏、数据累积、偶发失败）只有重复运行才暴露。
   比如档次库的重复累积问题，是**连跑两遍完整链路**才发现的。

# 八、反思与局限

## Q30. 这个项目最大的不足是什么？

**回答**：诚实说四点。

**① 没有独立测试集，泛化能力只能估计**
教师只提供了 train/val，我们所有选择（阈值、模型、TTA）都基于同一个验证集。
虽然做了 5 折交叉验证来量化乐观偏差，但**这不等价于一个真正没参与过任何选择的测试集**。

**② 剩余错误集中在任务设计的天花板**
61 张错误里，unknown 占 25 张 —— 这些是刻意挑的 `hard_negative`
（比如 MINI CLUBMAN 考你能否和 MINI 区分）。这部分要再提升，
需要专门针对近似款的训练策略（难例挖掘、对比学习），不是调参能解决的。

**③ 联网抓取受站点结构影响**
`browse_page` 的表格抽取针对汽车之家的配置页结构优化过。
换一个站点（懂车帝、易车）需要重新调选择器。目前是"能用但不通用"。

**④ 拒识机制比较朴素**
用的是"max softmax 概率 + 全局阈值"。学术界有更好的 OOD 检测方法
（Energy-based、Mahalanobis 距离、专门训练的二分类器）。
我们选了最简单可解释的方案 —— 在这个规模下够用，但不是最优。

## Q31. 如果重做一遍，你会先做什么？

**回答**：

1. **先把分辨率定下来再开工**。我们从 160 → 224 → 288 → 352 走了一路，
   前面两组实验（160 的基线）几乎白做 —— **分辨率的影响远大于其他所有超参**。
2. **一开始就建好 `tools/reproduce_production.py`**。实验代码和生产代码不一致
   这个坑，让 0.9815 一度变成假的 0.9695。
3. **数据管道的性能一开始就量**。我们用 `num_workers=0` 训练了很久，
   实测 GPU 有 **79% 的时间在等数据** —— 白白浪费了几个小时。

## Q32. 学到了什么？

**回答**：三条比技术更重要的。

**① 测量优于猜测。** 训练慢，我第一反应是"GPU 不行"，实际是数据管道；
分数上不去，我以为是"模型不够好"，实际是**分辨率看不清**。
每次老老实实分段计时/分档统计，都比猜得快。

**② 不要相信"看起来该有用"的方法。** 这次试了四种提升手段：
多尺度 TTA ❌、快照集成 ❌、调阈值 ❌、弱模型集成 ❌ ——
**四个"理论上可行"的方法全部失败**，而真正有效的是最朴素的"让模型看得更清"。

**③ 不报错的 bug 最难查。** 缓存不看权重、标定口径不一致 ——
这类问题不会崩、不会报错，只是"结果莫名不对"。
**所以关键指标要人工复核，不能只看流程跑没跑通。**
