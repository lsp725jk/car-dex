# 15 · 微调实战指南

> 这篇讲**怎么在已经训练好的模型上继续学**，以及背后的每一项技术。
>
> 微调看起来只是"再训一遍"，但**学习率、冻结哪几层、数据怎么组织**这三件事
> 只要有一件做错，就会得到一个"新的学会了、旧的忘了"的模型。
> 本文把每一步的道理和实测数据都摊开写。

---

## 1. 先分清三件事

很多人把这三个概念混在一起，但它们的**训练目标完全不同**：

| | 骨干（特征提取器） | 分类头 | 适用场景 | 本项目对应 |
| --- | --- | --- | --- | --- |
| **从头训练** | 随机初始化，全训 | 全训 | 数据充足（几万张以上） | `pretrained=False` |
| **迁移学习** | 用 ImageNet 预训练权重，全训 | 全训 | 数据中等（几千张） | 任务一的 C1/C2 就是这个 |
| **微调（fine-tune）** | **已经在本任务上训好了**，再动一动 | 再动一动 | 有新数据 / 新分布 / 想再提升 | 就是这篇 |

**关键区别**：

* 迁移学习的起点是 **ImageNet 的 1000 类通用特征** —— 那时模型还不知道什么是"轩逸"；
* 微调的起点**已经认得这 50 款车了**（本项目的 `improved_resnet50_224`，验证集 Macro-F1 0.9571）。

所以微调要解决的问题不是"从零学会认车"，而是"**在不把已学会的东西弄丢的前提下，
再适应一点新情况**"。这个约束决定了后面所有参数的选择。

---

## 2. 三种冻结模式：改动越少越安全

`--mode` 控制"哪些层参与更新"。项目实测的参数量对比（ResNet18，51 类）：

| 模式 | 冻结什么 | 可训练参数 | 占比 | 什么时候用 |
| --- | --- | --- | --- | --- |
| `head` | 整个骨干 | 26,163 | **0.2%** | 数据很少（几百张以内）、或只要"换批标签" |
| `partial` | `conv1/bn1/layer1/layer2` | 10,519,603 | 93.9% | **默认推荐**：数据中等，只动深层语义 |
| `full` | 不冻结 | 11,202,675 | 100% | 数据充足（上千张）、且和原分布差别大 |

### 为什么按"层深"划分

卷积网络的层级是有明确分工的：

```
conv1 / bn1 / layer1 / layer2   ← 边缘、纹理、颜色块   （通用，跨任务都能用）
layer3 / layer4                 ← 部件、结构、整体形状 （开始和具体任务相关）
fc                              ← 具体类别             （完全任务相关）
```

浅层学的是"**所有图像都有**"的东西 —— 无论你拍车还是拍猫，边缘和纹理都是一样的。
动它没有任何好处，只有坏处（把通用能力弄坏）。所以 `partial` 模式冻结浅层、只训深层。

### 实测：head 模式快得离谱

```
$ python src/finetune.py --from improved_resnet50_224 --mode head --epochs 4

冻结策略：head —— 冻结 159 个参数张量，可训练 104,499 / 23,612,531（0.4%）
epoch 1/4  train_loss=0.4636 train_acc=0.9933 | val MacroF1=0.9585
epoch 3/4  train_loss=0.4573 train_acc=0.9924 | val MacroF1=0.9596  ← 最佳
epoch 4/4  train_loss=0.4540 train_acc=0.9936 | val MacroF1=0.9590

最佳模型验证结果：Macro-F1=0.9593    总用时 4.1 分钟
```

三个值得注意的现象：

1. **第 1 轮 train_acc 就 99.3%** —— 因为特征早就是现成的，只是重新拟合一个线性层，
   几十个梯度步就够了。这从侧面证明了**骨干提取的特征质量很高**。
2. **每轮只要 16 秒**（ResNet50 全量微调需要 30 秒/轮）—— 只有 0.4% 的参数有梯度。
3. **train_acc 99.4% vs val_acc 94.7%** —— 这就是**过拟合**的典型特征：
   模型把训练集背下来了，但泛化没有同步提升。
   只训分类头时这是常态（分类头容量小，只能靠"记住"来降训练损失）。

> 这也说明：**head 模式不是用来提升精度的**，它是用来"快速适配"的。
> 真要提升精度得放开更多层（`partial` 或 `full`）。

## 3. 学习率：微调翻车的头号原因

这是整篇最重要的一节。

### 为什么不能沿用从头训练的学习率

任务一从头训练用的是 `lr = 0.01`（SGD + 余弦退火）。
如果微调也用 0.01，会发生**灾难性遗忘（Catastrophic Forgetting）**：

```
第 1 轮：模型先把已学好的特征"撞坏"（大梯度把权重推离原来的好位置）
第 2 轮：从一个坏起点重新学
结果：小数据上根本学不回来，最终精度比微调前还差
```

因为微调的起点**已经在一个很好的极小值附近**了，大步长只会把它踢出去。

### 项目内置的学习率配方

脚本按 `--mode` 自动给推荐值（见 `src/finetune.py` 的 `LR_RECIPE`）：

| 模式 | 默认 lr | 相对从头训练 | 理由 |
| --- | --- | --- | --- |
| `head` | **1e-3** | 0.1× | 只更新一个线性层，参数量极小，可以放心用大 |
| `partial` | **2e-4** | 0.02× | 深层要适应新数据，但不能冲太猛 |
| `full` | **5e-5** | **0.005×（小 200 倍）** | 所有层都会动，必须极小心 |

**一句话原则**：**改动越多的部分，学习率越小。**

### 分类头单独给更高的学习率

```python
# 骨干用 base_lr，分类头用 base_lr × head_lr_mult
groups = param_groups(model, base_lr, head_lr_mult=5.0)
```

理由：换了类别数时分类头是**随机重新初始化**的，而骨干是训练好的。
两者"成熟度"差得远，用同一个学习率必然有一方不合适。

> ⚠️ 项目早期踩过反向的坑：把 `head_lr_mult` 设成 **10** 配 `lr=0.01`，
> 结果 `val_loss` 飙到 **2889**、Macro-F1 只有 **0.007** —— 分类头被推飞了。
> 后来固定成 `1.0`（不分开放）才稳。

## 4. LLRD：逐层递减学习率

比"骨干/分类头两档"更细的做法：**按层深给一串递减的学习率**。

`--llrd` 打开后，本项目实测的分组（`base_lr=1e-3, decay=0.75`）：

```
depth=  0  lr=3.13e-05   conv1 + bn1        ← 最慢：几乎不动
depth=  1  lr=6.25e-05   
depth=  2  lr=1.25e-04   layer1
depth=  3  lr=2.50e-04   layer2
depth=  4  lr=5.00e-04   layer3
depth=  5  lr=1.00e-03   layer4             ← 最快：充分适应新数据
depth= 99  lr=1.00e-03   分类头
```

公式：`lr(depth) = base_lr × decay^(max_depth − depth)`

**为什么比"两档"更好**：它承认了一个事实 ——
"浅层该少动、深层该多动"**不是一个开关，而是一个连续谱**。
浅层不是"完全不能动"，只是"动一点点"；深层也不是"随便动"，而是"动得多一些"。

这在**小数据**上尤其明显：数据越少，越要用这种"温柔"的方式，
否则模型会把预训练阶段辛苦学到的通用特征覆盖掉。
（这个技巧来自 BERT/ViT 的微调实践，CNN 上同样有效。）

## 5. 渐进解冻：先接头，再练身

`--progressive-unfreeze N`：**前 N 轮只训分类头，之后才放开骨干**。

```python
# 第 N+1 轮开始时
freeze_by_mode(model, "full")       # 只需要切换 requires_grad
```

**为什么这样安排**：

1. 刚换数据时，分类头是随机/不匹配的，**它的梯度会很大**；
2. 如果这时骨干也在更新，这些大梯度会顺势把骨干也推歪；
3. 先花几轮把分类头练到"不瞎指"，再放开骨干，训练会稳很多。

### 一个实现细节：优化器要一开始就持有全部参数

```python
# 正确：优化器建组时就包含冻结参数
groups = param_groups(model, lr, include_frozen=True)
optimizer = SGD(groups, ...)
freeze_by_mode(model, "head")          # ← 之后才冻结
...
freeze_by_mode(model, "full")          # ← 解冻只是切开关，不动优化器
```

**不要**在解冻时重建优化器 —— 那会丢掉 SGD 的动量缓冲区 / AdamW 的二阶矩，
是个**看不见的性能损失**（模型还能训，但收敛会变慢、变抖）。
冻结的参数没有梯度，优化器会自动跳过，零开销。

## 6. 用自己的数据微调（领域适配）

### 数据怎么放

目录名必须是**类别 ID**（四位数字），和 `classes.txt` 里的对应：

```
D:\my_car_photos\           ← --data 指向这里
├── 0003\                   ← 宇通客车_宇通T7
│   ├── IMG_0001.jpg
│   └── ...
├── 0975\                   ← 日产_轩逸
│   └── ...
└── unknown\                ← 如果拍了"不在 50 款里"的车，放这里
    └── ...
```

**不在 `classes.txt` 里的目录名会被直接忽略** —— 这样你可以把照片随手丢进去，
不用担心某个文件夹名不对就让整次训练失败。

### 一张图都没有验证集怎么办

```bash
# 显式声明没有验证集：用训练集自己评估
python src/finetune.py --from improved_resnet50_224 --data D:\photos --val-data none
```

引擎会打一条**明确的警告**：

> 没有找到独立的验证集目录，本次验证用的就是训练集 ——
> 指标只反映拟合程度，**不能当作泛化能力**。

### 默认仍用原来的验证集（推荐）

不传 `--val-data` 时，验证还是跑 `data/val`（原始 51 类）。
这样做的好处是：**你能立刻看到"自己的照片训完之后，原来那 51 类的本事有没有被弄坏"**。

这是微调最常见的翻车方式 —— 新任务学会了，老任务忘了，而如果不测老任务你根本发现不了。

### 实测

```
$ python src/finetune.py --from improved_resnet50_224 --mode head --epochs 3 \
      --data E:\my_photos      # 36 张图 / 3 个车型

训练集 36 张 / 3 类（E:\my_photos）
验证集 2422 张 / 51 类（data\val）        ← 仍在测原来那 51 类
epoch 3/3  train_acc=0.9167 | val_acc=0.9451 MacroF1=0.9571   ← 原有能力没被破坏
总用时 2.5 分钟
```

## 7. 微调的参数该和从头训练不一样

`src/finetune.py` 里有意做了几处与任务一不同的默认值，都有理由：

| 参数 | 从头训练 | **微调** | 为什么 |
| --- | --- | --- | --- |
| `epochs` | 14~18 | **8** | 起点已经很好，训多了只会过拟合 |
| `lr` | 1e-2 | **5e-5 ~ 1e-3** | 见第 3 节 |
| `train_transform` | `strong_train` | **`moderate_train`** | 模型已经学得不错，强增强会让它"退步" |
| `randaugment` | 开 | **关**（除非 `--strong-aug`） | 同上 |
| `RandomErasing` | 0.25 | **0**（除非 `--strong-aug`） | 同上 |
| `mixup/cutmix` | 0.2 / 0.5，prob 0.35 | **关** | 混合样本会拖慢收敛，而微调轮数本来就少 |
| `label_smoothing` | 0.1 | **0.05** | 起点已经不太"过度自信"了，不需要压那么狠 |
| `warmup_epochs` | 2 | **1** | 微调没那么多轮可以浪费在预热上 |

> **核心思路**：从头训练是"从零开始，需要强正则防过拟合"；
> 微调是"站在巨人肩上，需要**温柔**，别把巨人推倒"。

## 8. 完整命令速查

```bash
# ① 只看计划，不训练（先确认参数对不对）
python src/finetune.py --from improved_resnet50_224 --mode partial --dry-run

# ② 小数据快速适配：只训分类头
python src/finetune.py --from improved_resnet50_224 --mode head --epochs 12 --data D:\photos

# ③ 领域适配（推荐）：训深层 + 逐层递减学习率
python src/finetune.py --from improved_resnet50_224 --mode partial --llrd --epochs 8 --data D:\photos

# ④ 数据充足时全量微调
python src/finetune.py --from improved_resnet50_224 --mode full --lr 3e-5 --epochs 6

# ⑤ 渐进解冻：前 2 轮只接头，之后放开
python src/finetune.py --from improved_resnet50_224 --mode full --progressive-unfreeze 2 --epochs 8

# ⑥ 数据多、想用强增强
python src/finetune.py --from improved_resnet50_224 --mode partial --strong-aug --epochs 10
```

微调完之后接下游：

```bash
python src/evaluate.py --checkpoint outputs/checkpoints/<run>/best.pt --tta-hflip
python src/finalize.py --candidates <run> improved_resnet18_224 improved_resnet50_224 \
                       --ensembles <run>+improved_resnet18_224
```

## 9. 常见翻车方式

| 现象 | 原因 | 怎么修 |
| --- | --- | --- |
| 微调后精度**比微调前还差** | 学习率太大，灾难性遗忘 | 把 lr 降一个数量级（`full` 从 1e-4 降到 1e-5） |
| train_acc 99% 但 val_acc 不动 | 只训了分类头，它在"背题" | 换 `partial` / `full`，放开更多层 |
| **新类别学会了，老类别忘了** | 没测原有能力 | 保留 `data/val` 做验证；或降低 lr；或用 LLRD |
| 一开始 loss 就爆炸 | 换类别数后分类头是随机的，梯度太大 | 加 warmup、开 `--progressive-unfreeze`、或者先把 head 冻结几轮 |
| 训了几轮 val 指标纹丝不动 | 学习率太小 / 冻结太狠（`head` 模式下骨干本来就不会变） | 检查 `lr` 和 `--mode` |
| 自定义数据目录读不到图 | 目录名不是四位类别 ID | 目录必须叫 `0003` 这种，见第 6 节 |
| `unknown 检出率 = —` | 验证集里没有 unknown 样本 | 正常现象（指标无定义），补一批 unknown 图即可 |

## 10. 想加"新的车型"怎么办

当前模型只认 `classes.txt` 里的 50 款。要认新车，需要：

1. **改类别定义**：`classes.txt` 加新 ID（仍要升序、四位数字），
   同步更新 `configs/class_map.json` 的映射，`num_classes` 从 51 变成 51+N；
2. **准备数据**：新车型的照片目录，以及**要重新划一部分 unknown 来源**
   （原来当 unknown 的类如果被选进来了，就不能再当 unknown 了 —— 会数据泄漏）；
3. **用微调复用已学特征**：`load_weights_into()` 在类别数不同时会**自动跳过分类头**，
   只装骨干 —— 实测目标 60 类时，320 个张量里 318 个骨干装上了、2 个分类头重新初始化；
4. **重训**：`python src/finetune.py --from improved_resnet50_224 --mode partial --epochs 12`

> ⚠️ 注意这是**破坏性**的：`classes.txt`、`predictions.csv`、模型类别数、智能体的
> `car_profiles.json` 全都要跟着改。任务书规定必须**恰好 50 行**，
> 所以"加新车型"只适合做实验，不适合直接改交付物。

## 11. 实战案例：用**原来的数据**微调，把集成推高

「不能用原来的图片微调吗？」——**能，而且这是最实用的用法之一**。
关键是想清楚目的：**不是"再练一遍会更好"，而是"造一个不一样的好模型来集成"**。

### 实验设计

现有冠军是 **resnet18@224 + resnet50@224** 两人集成（0.9625）。
要让它更强，第三个成员必须**和这两个都不一样** —— 而"换输入分辨率"是最直接的多样性来源：
车型识别是细粒度任务（A6 vs A6L），**不同尺度看到的细节不同**。

```bash
python src/finetune.py --from improved_resnet50_224 \
    --mode partial --llrd --image-size 288 --epochs 6 --batch-size 24 \
    --run-name ft_r50_288
```

* 起点：resnet50@224（已训好，val Macro-F1 0.9571）
* 换成 **288×288**（像素量是 224 的 1.65 倍）
* `partial` + LLRD —— 只动深层，浅层几乎不动
* 6 轮，**9.2 分钟**（GPU）

### 结果：单独更差，集成更强

| 组合 | 标定后 Macro-F1 |
| --- | --- |
| `improved_resnet18_224` 单独 | 0.9507 |
| `improved_resnet50_224` 单独 | 0.9597 |
| **`ft_r50_288` 单独** | **0.9563** ← 比它爹还差 |
| `18 + 50`（原冠军） | 0.9625 |
| `18 + ft_r50_288` | 0.9635 |
| `50 + ft_r50_288` | 0.9604 |
| **`18 + 50 + ft_r50_288`** | **0.9646** ← 新冠军 |
| `18 + 50 + ft_r50_288 + baseline_160` | 0.9549 ← **被拖累** |
| `baseline_resnet18_160` 单独 | 0.8648 |

**两个结论：**

1. **集成成员不需要"单独最强"。** `ft_r50_288` 自己只有 0.9563（低于父模型 0.9597），
   但加进集成后把整体从 0.9625 推到 **0.9646**。
   原因是它**在 288 的尺度上看问题**，误判的样本和 224 的成员不一样 —— 正好互补。
   集成的价值来自**成员之间的差异**，不是单个成员的高度。

2. **多样性必须以"不弱太多"为前提。** `baseline_resnet18_160`（0.8648）确实和谁都不同，
   但太弱了，加进去把集成从 0.9646 拉回 **0.9549**。
   一个又弱又怪的成员只会投票投错。

> **诚实说明**：这一步是在**验证集上从 5 种组合里挑出来的**，
> 所以 0.9625 → 0.9646 这 +0.0021 里有一部分是"选择偏差"，真实泛化提升可能更小。
> 任务书要求阈值必须由验证集确定，选集成组合同理 —— 但**试的组合越多，乐观偏差越大**。
> 更严谨的做法是留一个从没参与过任何选择的测试集。

### 怎么复现

```bash
# 1) 微调出这个多样成员
python src/finetune.py --from improved_resnet50_224 --mode partial --llrd \
    --image-size 288 --epochs 6 --batch-size 24 --run-name ft_r50_288

# 2) 和现有成员一起比选（会自动挑出最好的组合）
python src/finalize.py \
    --candidates improved_resnet18_224 improved_resnet50_224 ft_r50_288 \
    --ensembles improved_resnet18_224+improved_resnet50_224 \
                improved_resnet18_224+improved_resnet50_224+ft_r50_288 \
    --tta-hflip
```

## 12. 完整案例：0.9646 → **0.9815**（+0.0169）

这一节记录从 0.9646 冲到 0.9815 的完整过程。**四个方法里两个有效、两个无效**，
无效的那两个同样值得记 —— 它们解释了为什么"看起来该有用"的手段其实没用。

### 起点与目标

```
当前（三人集成 + hflip TTA）：0.9646
目标：0.975 ~ 0.98
差距：+0.0104 ~ +0.0154
```

先做**误差结构分析**（`tools/analyze_errors.py`）再动手，不猜：

```
总错误 113 张 / 2422
  已知类被判 unknown    65 张
  unknown 被误认成车型  37 张
反事实：
  unknown 全判对          → 0.9746
  已知类那 65 张全认对     → 0.9842   ← 最高杠杆在这
```

### 方法一：提高分辨率 ✅ **+0.0106**

**第一次尝试（失败）**：把 224 训好的模型拿到更高分辨率上推理：

| 模型 | @224 | @288 | @352 |
| --- | --- | --- | --- |
| `improved_resnet50_224` | 0.9597 | 0.9509 | 0.9236 |
| `improved_resnet18_224` | 0.9507 | 0.9354 | 0.8926 |

**性能是掉的。** 训练时模型只见过 224 的尺度，推理时给它 288 的图，
特征分布对不上 —— 这叫**训练/测试分辨率不匹配**。

**正确做法**：**在目标分辨率上从零训练**。

```bash
python src/train.py --config configs/train_r50_288.json   # ResNet50 @288, 20 epochs
python src/train.py --config configs/train_r50_352.json   # ResNet50 @352, 20 epochs
```

| 模型 | 训练耗时 | 原始 Macro-F1 | 标定后 |
| --- | --- | --- | --- |
| `r50_288_from_scratch` | 30.7 min | 0.9739 | 0.9752 |
| `r50_352` | 40.9 min | **0.9756** | 0.9781 |

**单个模型就超过了原来的整个集成**（原始 0.9739 vs 集成标定后 0.9646）。

> **为什么分辨率这么关键**：车型识别是细粒度任务。"朗逸"和"宝来"差在格栅条纹、
"A6"和"A6L"差在后门长度 —— 这些特征在 224×224 下只剩几个像素。
模型不是不够聪明，是**看不清**。

### 方法二：多裁剪 TTA ✅ **+0.0025**

这里要区分两个名字很像、效果完全相反的东西：

| | 做什么 | 结果 |
| --- | --- | --- |
| **多尺度 TTA** | 把图缩放到训练时**没见过**的尺寸 | ❌ 0.9651（几乎没用） |
| **多裁剪 TTA** | **保持训练分辨率**，只换裁剪位置（中心 + 四角） | ✅ **0.9779**（+0.0027） |

多裁剪为什么有效：区分车型的关键部位（进气格栅、大灯）**不一定落在画面正中央**。
五个裁剪位置相当于让模型"多看几眼"，而且每个位置的尺度是它熟悉的。

```python
# src/cardex/inference.py
transforms.FiveCrop(crop)        # 中心 + 左上/右上/左下/右下
views = 5 × 2(水平翻转) = 10 个视角
```

代价：推理时间约 **5 倍**（63 ms → 200 ms）。对 Web 交互完全可接受。

### 方法三：快照集成 ❌ **-0.0017**

同一次余弦退火训练会保存多个 epoch 的权重（`epoch_12/15/18/last`）。
把这些快照的预测平均起来，理论上能免费得到一个小集成（Huang et al. 2017）。

**实测是负收益：**

| 快照 | 单独 Macro-F1 |
| --- | --- |
| `epoch_12` | 0.9710 |
| `epoch_15` | 0.9727 |
| `epoch_18` | 0.9738 |
| `last` | **0.9752** |
| 四个平均 | **0.9735**（-0.0017） |

**原因**：同一次训练轨迹里的快照**相关性太高**（模型走的几乎是同一条路），
而且强度不齐（0.9710 vs 0.9752）—— 平均起来就被弱的那个拖低。
**多样性必须来自"不同训练"，不能来自"同一次训练的中间产物"。**

### 方法四：两个强模型集成 ✅ **+0.0009**

之前所有的集成尝试都失败了，原因都一样：**强 + 弱 = 弱**。

| 组合 | 标定后 Macro-F1 |
| --- | --- |
| `r50_288` + `improved_resnet50_224`（0.9597） | 0.9732 ← 被拉低 |
| `r50_288` + `improved_resnet18_224`（0.9507） | 0.9719 ← 被拉低 |
| `r50_288` + 三个 224 模型 | 0.9725 ← 被拉低 |
| **`r50_288`（0.9752）+ `r50_352`（0.9781）** | **0.9815** ← 两个都强 |

**等权平均里，弱成员是负资产。** 集成要的是"**同样强、但犯错的地方不一样**"，
不是"多凑几个"。288 和 352 分辨率不同 → 看问题的尺度不同 → 有真实多样性。

### 最终结果

```
★ 288+352 @中心+五裁剪   →   Macro-F1 = 0.9815
  τ = +0.10   t = 0.20   Accuracy = 0.9748
  unknown 检出率 0.963   已知类误拒率 0.019
  总错误 61 / 2422（3.26% → 2.52%）
```

| | 旧冠军 | **新冠军** |
| --- | --- | --- |
| 配置 | 3 个 224 模型 + hflip | **2 个 288/352 模型 + 多裁剪** |
| Macro-F1 | 0.9646 | **0.9815** |
| 总错误 | 113 张 | **61 张** |
| 推理耗时 | 132~144 ms | 200~240 ms |

### ⚠️ 踩到的坑：标定口径必须和生产推理口径逐字节一致

实验脚本里多裁剪算出了 **0.9815**，但用**生产代码**（`CarEnsemble`）复现只有 **0.9695** —— 差 0.012。

**根因在两组视角的加权方式**：

```python
# 实验脚本：中心组和五裁剪组【等权】
(center_lp + five_lp) / 2

# 生产代码第一版：把两组直接相加，再除以 (2+5)
lp = lp + lf        # = 2×中心 + 10×五裁剪
return lp / 7       # → 中心 2/7、五裁剪 5/7  ← 不一致！
```

**后果**：τ 和拒识阈值是在"50/50 口径"下标定的，用到"2/7 vs 5/7 口径"上当然不对。

**教训**：

> **标定用的推理口径，必须和上线时的推理口径逐字节一致。**
> 否则你标出来的 τ/t 全是错的，而且**不会报任何错** —— 指标只是"莫名变差"。
>
> 排查方法见 `tools/reproduce_production.py`：用**生产代码**跑一遍验证集，
> 和实验脚本的数字对比。差异 > 0.003 就说明两个实现不一致。
> 修好之后复现差异是 **+0.0000**。

### 顺带踩的另一个坑：多裁剪会压平概率分布

```
同一张图（预测正确）：
  单视角    置信度 0.9854
  hflip     置信度 0.9792
  多裁剪    置信度 0.6291   ← 掉到三分之一
```

因为 10 个视角里有 4 个角落裁剪可能是天空/背景，平均后分布变平。
**这意味着换 TTA 档位后必须重新标定拒识阈值**（实测最优 t 从 0.30 降到 0.20），
沿用旧阈值会大量误拒。

### 方法论总结

| 手段 | 有效？ | 增益 | 成本 |
| --- | --- | --- | --- |
| 提高训练分辨率 224→288 | ✅ | +0.0106 | 30 min GPU |
| 多裁剪 TTA | ✅ | +0.0025 | 推理 ×5 |
| 提高分辨率 288→352 | ✅ | +0.0029 | 41 min GPU |
| 两个强模型集成 | ✅ | +0.0009 | 推理 ×2 |
| 多尺度 TTA | ❌ | +0.0005 | 推理 ×3 |
| 快照集成 | ❌ | -0.0017 | 免费 |
| 调拒识阈值 | ❌ | -0.0011 | 免费 |
| 弱模型加入集成 | ❌ | -0.003 ~ -0.01 | 推理 ×N |

**一句话**：**先让模型"看得更清"（分辨率），再让它"多看几眼"（多裁剪），
最后用"同样强但不一样"的伙伴互相补位（集成）。**
调阈值、凑成员、变尺度这些"看起来聪明"的招，在模型本身不够强时都没有意义。
