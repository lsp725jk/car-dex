## 5. 智能体设计

### 5.1 DeepSeek 接入方式

| 项目 | 做法 |
| --- | --- |
| 接口 | DeepSeek 开放平台 `/chat/completions`（`https://api.deepseek.com/chat/completions`） |
| 模型名 | **`deepseek-v4-flash`**（在 `agent/config.py::MODEL_NAME` 中固定为常量，不出现在任何可配置的地方） |
| 调用方式 | `requests` 直接 POST，非流式；`temperature=0.2`、`max_tokens=2048`、`tool_choice="auto"` |
| **API Key 管理** | 优先读环境变量 `DEEPSEEK_API_KEY`，其次读本地文件 `agent/.env.local`；**两者都不存在时进入离线替身模式**。仓库只提供 `agent/.env.example`（占位符 `sk-REPLACE_WITH_YOUR_OWN_KEY`），`.gitignore` 已忽略 `.env.local` |
| Key 的日志处理 | `Config.masked_key()` 只返回 `sk-1…abcd（长度 51）` 这样的脱敏形式；请求头从不打印。自查脚本会扫描全部提交文件，确认没有 `sk-[A-Za-z0-9]{20,}` 形式的真实 Key（实测 0 处命中） |

**核心设计**：模型不接收图片。图片由 Web 端上传后绑定到会话，
模型只能看到「本会话已上传图片」这一个事实，**必须调用 `classify_car` 才能拿到识别结果**。
这满足任务书 5.1 节「视觉识别必须通过智能体工具调用执行」的要求——
不存在"后台先识别好再拼进 Prompt"的路径。

### 5.2 工具定义

共 **8 个工具**（任务书要求 ≥1 视觉 + ≥2 其他，本项目 1 + 7）：

| 工具 | 类型 | 参数（`?` = 可选） | 超时 | 失败处理 |
| --- | --- | --- | --- | --- |
| `classify_car` | **视觉** | `image_path?` `top_k?` | 120 s | 图片缺失/损坏/模型未加载 → 对应错误码 + 修正建议 |
| `query_car_info` | 知识 | `car_id_or_name`（必填） | 10 s | 查不到 → `CAR_NOT_FOUND`，多义时附候选列表 |
| `list_supported_cars` | 知识 | `body_group?` `brand?` | 10 s | — |
| `add_car_record` | 档案 | `car_id?` `note?` `confidence?` `image_path?` | 15 s | 写入 unknown → `UNKNOWN_CAR` 拒绝 |
| `search_my_records` | 档案 | `keyword?` `car_id?` `brand?` `body_group?` `scope?` `limit?` | 15 s | — |
| `update_record_note` | 档案 | `record_id`（必填）`note?` | 15 s | 记录不存在 → `RECORD_NOT_FOUND` |
| `delete_car_record` | 档案 | `record_id`（必填） | 15 s | 同上 |
| `my_garage_stats` | 档案 | `scope?` | 15 s | — |

**执行流水线**（`agent/tools/registry.py`，7 步）：
查表 → 解析 JSON → Schema 校验 → 前置门禁 → 执行主体（超时 + 协作式取消）→ 后置处理 → 写调用记录。

失败一律返回结构化结果，**不伪造成功**：

```json
{
  "ok": false,
  "error": {
    "code": "CAR_NOT_FOUND",
    "message": "资料库里没有与「保时捷911」匹配的车型",
    "hint": "本资料库只收录 50 款车型，可用 list_supported_cars 查看全部清单"
  },
  "retryable": false
}
```

共定义了 **20 个错误码**（`agent/errors.py`），覆盖工具调度、视觉、资料库、模型与网络四层。

### 5.3 连续工具调用流程（任务书 5.3）

**任务设计**：用户上传车照并说「这是什么车？介绍一下，然后加进我的收藏。」

```
用户上传图片 + 提出任务
   ↓
Agent 调用 classify_car          返回 car_id / car_name / confidence
   ↓  car_id 作为下一步输入
Agent 调用 query_car_info       用同一个 car_id 查档案
   ↓  确认车型存在
Agent 调用 add_car_record       再用同一个 car_id 写入档案
   ↓
Agent 汇总结果并回答用户
```

**前后结果的衔接关系**（这是任务书要求说明的重点）：

| 步骤 | 输入来自 | 输出交给 |
| --- | --- | --- |
| `classify_car` | 会话绑定的图片（模型看不到图，只传空参数） | `car_id` → `query_car_info` |
| `query_car_info` | 上一步的 `car_id` | 车型档案 → 用于组织回答 |
| `add_car_record` | 上一步同一个 `car_id`（可省略，自动沿用） | 记录 ID → 用于回答中的确认 |

**由程序实际执行**：三个工具都在 `ToolRegistry.execute()` 里真实运行，
结果写入 `agent/data/tool_calls.jsonl`。**实测记录见第 7.2 节。**

### 5.4 Session 与多轮对话（任务书 5.4）

**会话真身是一份 append-only 的事件日志**（`agent/data/sessions/<id>.jsonl`），
内存对象只是它的投影。事件类型与用途：

| 事件 | 载荷 | 作用 |
| --- | --- | --- |
| `session_meta` | 模型、离线标记、视觉模型路径、阈值、提示词版本 | 会话头 |
| `turn_context` | 本轮图片、阈值、工具清单、轮数上限 | **一次 turn 一个策略快照** |
| `user_message` / `assistant_message` | 消息内容 | 对话历史 |
| `tool_result` | 工具名、参数、结果、耗时、错误码 | 工具调用记录 |
| `error` | 错误码、消息、提示 | 异常留痕 |
| `turn_end` | 轮数、工具链、总耗时 | 一轮收束 |

**多轮对话的上下文保持**：`Agent._absorb()` 在工具成功后把结果吸收进会话状态：

```python
if tool_name == "classify_car":
    session.last_prediction = {car_id, car_name, confidence, is_unknown, decision, image}
elif tool_name == "add_car_record":
    session.record_count = payload["total_records_in_session"]
```

由此实现两个关键行为：

1. **第二轮无需重新上传**：用户只说「帮我记录下来」时，模型可以省略 `car_id`，
   `add_car_record` 自动沿用 `session.last_prediction`（实测返回 `resolved_from = from_last_prediction`）。
2. **换新图片会重新识别**：会话记录上一次识别所依据的图片名，
   若与当前 `session.image_path` 不一致，视为结论过期，必须重新调用 `classify_car`。

**会话可重放**：`SessionStore.get()` 在内存未命中时会重放 JSONL 恢复状态——
实测从一个 81 条事件的日志恢复出 65 条模型可见消息。

### 5.5 低置信度与 unknown 处理（任务书 5.5）

本系统有**三个由验证集确定的数值**，用途严格区分：

| 名称 | 取值 | 性质 | 来源 |
| --- | --- | --- | --- |
| 先验校正 τ | +0.05 | 模型决策 | 任务一 `src/finalize.py` 扫 204 组 (τ,t) |
| **拒识阈值 t** | 0.25 | 模型决策（`< t` 改判 unknown） | 同上 |
| **低置信度提示阈值 c** | **0.70** | **仅影响智能体措辞**，不改变判定 | `tools/derive_confidence_threshold.py` |

**c = 0.70 的推导**（验证集 2,422 张的选择性预测分析）：

| c | 自动接受比例 | 这批样本准确率 | 剩余样本准确率 |
| --- | --- | --- | --- |
| 0.60 | 87.6% | 97.97% | 69.67% |
| **0.70** | **82.9%** | **98.51%** | **74.88%** |
| 0.85 | 69.0% | 99.40% | 83.49% |

即：置信度 ≥ 0.70 的预测，98.5% 是对的；低于 0.70 的只有 74.9% 是对的。

**结构化决策建议**：`classify_car` 不只返回数字，还把"该走哪条分支"编码成字段：

```json
"decision": {
  "action": "report_unknown",       // accept | confirm_with_user | report_unknown
  "guidance": "模型判定该车不属于本组支持的 50 款车型。请如实告知用户…"
}
```

| action | 触发 | 智能体行为 |
| --- | --- | --- |
| `accept` | 置信度 ≥ 0.70 且非 unknown | 继续查询档案、写入记录 |
| `confirm_with_user` | 置信度 < 0.70 | 展示 Top-K、请用户确认、提示重拍；**确认前不写入档案** |
| `report_unknown` | `is_unknown = true` | 告知「未识别为本组支持的车型」；不编造、不继续业务 |

**双重保护**：即使模型判断失误，`add_car_record` 也会**主动拒绝**把 unknown 写入档案
（错误码 `UNKNOWN_CAR`），不会污染用户的资料库。

**关于"低置信度处理不能替代 unknown 训练"**：任务书这句话在本项目中得到了印证——
任务一的实测显示，主要错误是**高置信度错误**（模型以 0.99 的置信度把车型判成 unknown），
拒识阈值带来的 Macro-F1 增益只有约 +0.004。因此本项目把阈值定位为
「给用户的提示开关」，而非提升精度的手段。

## 6. Web 与工程实现

### 6.1 系统结构

```
浏览器（单页界面）
   │  POST /api/upload            图片上传 → 绑定到会话
   │  POST /api/chat              SSE 事件流
   ▼
Flask（web/app.py，threaded）
   │
   ├─ SessionStore   会话状态 + 事件日志（JSONL）
   │
   └─ Agent（agent/loop.py）
        ├─ prompts.py   分段组装系统提示词 + 动态运行时上下文
        ├─ llm.py       DeepSeekClient（真实）/ ScriptedClient（离线替身）
        └─ ToolRegistry 8 个工具 + 7 步执行流水线
             ├─ vision.py   → CarEnsemble → 任务一的 checkpoint（真实前向推理）
             ├─ profile.py  → agent/data/car_profiles.json
             └─ garage.py   → agent/data/garage.db（SQLite）
```

一条完整链路上的**每一层都可观测**：前端有工具调用卡片、后端有 SSE 事件、
落盘有 `tool_calls.jsonl` 与 `sessions/*.jsonl`。

### 6.2 主要页面

单页界面，分左右两栏：

| 区域 | 内容 |
| --- | --- |
| 顶部横幅 | 离线替身模式警告（仅在未配置 Key 时出现） |
| 顶栏 | 品牌、会话 ID、模型名、运行模式、视觉模型、新会话、暗色切换 |
| 左 · 对话区 | 消息气泡；**工具调用卡片**（可点开看完整参数与返回 JSON、耗时、成功/失败）；每条消息带元信息（轮数/工具次数/耗时） |
| 左 · 输入区 | 上传按钮、待上传图片预览（可移除）、输入框、发送 |
| 右 · 运行状态 | 模型、模式、API Key（脱敏）、视觉模型、三个阈值、工具数 |
| 右 · 我的看车档案 | 缩略图、车型名/ID、品牌·车身类型·置信度·时间、备注、删除；支持关键词与范围筛选 |
| 右 · 可用工具 | 8 个工具的名称、用途、参数标签 |

**交互细节**：
- 对话走 **SSE 流式**，工具卡片在调用发起时就出现（显示"调用中"），
  结果返回后原地变成成功/失败并补上耗时与结果 JSON，不需要刷新页面；
- 所有错误（上传失败、工具失败、模型失败、超轮数）都以红色卡片显示在对话流里，
  带错误码与 `hint` 修正建议；
- 支持暗色模式（跟随系统 + 手动切换 + localStorage 记忆）。

### 6.3 数据存储

| 数据 | 存储 | 说明 |
| --- | --- | --- |
| 车型档案（50 条） | `agent/data/car_profiles.json` | 由 `tools/build_car_profiles.py` 从教师 `class_info.json` + 本组 `selection.json` + `data_stats.json` 聚合生成 |
| **看车档案** | `agent/data/garage.db`（SQLite） | 表 `car_records`：session_id、car_id、car_name、brand、body_group、confidence、image_path、note、source、created_at、updated_at；按 session 隔离 |
| 会话事件日志 | `agent/data/sessions/<id>.jsonl` | append-only，每行一个事件，可重放 |
| 工具调用记录 | `agent/data/tool_calls.jsonl` | 每次调用一行：时间、会话、轮次、调用 ID、工具、参数、结果、耗时、错误码 |
| 上传图片 | `data/uploads/` | 校验扩展名 + 真实可解析 + 12 MB 上限 |

**关于车型档案的诚实说明**：教师数据集只提供类别 ID 与车型名称，
**没有排量、功率、价格、尺寸等参数**。因此档案只包含真实可得的信息
（ID、名称、品牌、车身大类与细分、看点、样本量），并在 `data_source` 字段写明每个字段的来源，
**不编造任何参数**。档案中的"看点"来自本组选类时逐条写下的人工理由，
不是模型生成的。

### 6.4 配置与异常处理

| 配置项 | 位置 | 说明 |
| --- | --- | --- |
| API Key | 环境变量 / `agent/.env.local` | 不含在代码里；仓库只提供 `.env.example` |
| 模型名 | `agent/config.py::MODEL_NAME` | 固定 `deepseek-v4-flash` |
| 视觉模型路径 | `agent/config.py::vision_checkpoints` | 默认 C1 + C2 两个 checkpoint，缺失时退化为可用单模型 |
| 三个阈值 | 由 `agent/data/confidence_threshold.json` 与 `finalize.py` 输出驱动 | 不硬编码 |
| 循环预算 | `max_rounds=8`、`max_tool_calls=16` | 超限明确报错 |

**异常处理清单**（12 类，均有对应错误码与用户可见提示）：

| 场景 | 错误码 | 页面表现 |
| --- | --- | --- |
| 没上传图片就要求识别 | `DEPENDENCY_MISSING`（前置门禁拒绝） | 工具卡片标红 + 「请先上传一张车辆照片」 |
| 上传非图片 / 图片损坏 | 上传接口直接 400 | 输入框下方提示 + 对话区错误气泡 |
| 图片文件被删除 | `IMAGE_NOT_FOUND` | 工具卡片标红 + 修正建议 |
| 视觉模型权重缺失 | `MODEL_NOT_LOADED` | 明确告知期望路径 |
| 未配置 API Key | `API_KEY_MISSING` | 启动时自动切离线模式，页面顶部横幅 |
| DeepSeek 接口失败 | `API_REQUEST_FAILED` | 红色错误卡（含 HTTP 状态与对应建议） |
| 输出被 max_tokens 截断 | `API_RESPONSE_INVALID` | 提示缩短回答 |
| 模型返回空内容 | `MODEL_REFUSED` | 提示重新发起 |
| 工具超时 | `TOOL_TIMEOUT` | 卡片标红 + 「请简化请求或稍后重试」 |
| 工具内部异常 | `TOOL_FAILED` | 如实显示异常类型，不掩盖 |
| 同一工具连续同样失败 3 次 | 熔断 → `MAX_ROUNDS_EXCEEDED` | 「同一个工具以相同方式连续失败多次，已停止以避免无效循环」 |
| 超过 8 轮 / 16 次调用 | `MAX_ROUNDS_EXCEEDED` / `MAX_TOOL_CALLS_EXCEEDED` | 明确报错，**不假装完成** |

**可以从中确认的五件事**：

1. **视觉工具是真实执行的** —— 第 1 轮 `classify_car` 耗时 8.7 秒，
   这是 CPU 上加载 C1+C2 集成模型并前向推理的真实耗时；第 3 轮因为模型已加载，只需 177 ms。
2. **三个工具构成完整业务链** —— 且 `add_car_record` 的来源是 `from_last_prediction`，
   说明它复用了 `classify_car` 的结果而不是重新识别。
3. **多轮上下文有效** —— 第 2 轮没有重新上传图片，会话仍能回答档案统计。
4. **unknown 被正确处理** —— 第 3 轮判定 `report_unknown`，且没有写入档案。
5. **每轮的策略快照完整** —— 每轮都有 `turn_context` 记录当轮绑定图片、工具数与运行模式。

### 7.3 测试中发现的问题及修复情况

| # | 问题 | 现象 | 根因 | 修复 |
| --- | --- | --- | --- | --- |
| 1 | **同一工具被重复调用直到熔断** | 日志显示 `my_garage_stats` 被连续调用 **8 次**，最终 `MAX_ROUNDS_EXCEEDED`：<br>`turn_end ok=False 轮数=8 工具=[my_garage_stats × 8]` | 离线替身在决定下一步时**把上一轮的工具调用也算作本轮已做**，于是反复执行同一个工具 | 只统计「最后一条 user 消息之后」的消息来判定本轮已调用的工具；同时给每个分支加上"若已调用则改为总结"的出口 |
| 2 | 有图时先查资料而不是先识别 | 用户说「这是什么车？介绍一下」，替身调用了 `query_car_info("这是什么车")` | 意图判定顺序错误：文本意图分支排在"有图先识别"之前 | 重排判定顺序：0) 有图未识别 → `classify_car`；1) unknown → 如实告知；2) 明确的文本意图；3) 已识别 → 资料/收藏链 |
| 3 | 替身不知道哪些工具调用过 | 工具结果里的 `_tool_name` 内部字段被 `public_messages()` 剥离（真实 API 也不接受该字段） | 用内部字段传递信息，与真实协议不一致 | 改为从历史里的 `assistant.tool_calls` 按 `tool_call_id` 反查工具名——与真实模型看到的信息完全一致 |
| 4 | 换新图片不重新识别 | 上传第二张车照问「这是什么车」，仍返回第一张的结果 | 只判断"是否识别过"，没判断"识别所依据的图片是否还是当前这张" | 会话记录 `last_prediction.image`，与 `session.image_path` 不一致时视为过期，强制重新识别 |
| 5 | 上传预览区一直显示 | 页面初次加载时"待上传图片"框可见，且显示破图图标 | CSS 里 `.attach-preview{display:flex}` 的优先级高于浏览器默认的 `[hidden]{display:none}` | 样式表增加 `[hidden]{display:none !important}` |
| 6 | 搜索关键词提取错误 | 「有没有记过轩逸」被当成整个句子去检索，匹配不到 | 关键词提取的正则没有剥离疑问与指令性措辞 | 扩充停用词表（有没有记过/我记过/找找/搜一下…），并先剥离再取车型名 |

**这些问题全部是在"无 API Key 的离线替身模式"下测出来的**，这也是设计离线替身的直接价值：
把"环境依赖"与"代码正确性"解耦，让工具链、会话、前端渲染的问题在没有网络和额度的情况下也能被发现。

### 8.2 存在的不足

| 不足 | 说明 | 改进方向 |
| --- | --- | --- |
| **未在真实 API 下完整验证** | 本机没有 `DEEPSEEK_API_KEY`，因此任务二三的功能验证是在**离线替身**下完成的。代码路径完全相同，但"真实模型是否会按预期调用工具"没有实测过 | 配置 Key 后重跑第 7.1 节的 12 个用例 |
| **车型档案信息量有限** | 教师数据集只给类别 ID 与名称，没有排量/价格/尺寸等参数，档案因此较薄 | 手工整理一份参数表（并标注来源），或接入公开的车型数据 |
| **无上下文压缩** | 单会话消息量小（< 20 条），未实现压缩；只做了工具结果截断（6000 字符）与失败熔断 | 消息数或 token 数超阈值时，先丢弃旧工具输出、再摘要历史 |
| **单机单进程** | 会话锁在进程内，多 worker 部署会失效 | 把会话状态与会话锁外置到 Redis 或数据库 |
| **无权限审批机制** | 保留了门禁钩子（`add_gate`）但默认策略宽松；本项目工具副作用仅限本机 SQLite，风险可控 | 若未来加入文件写入或 shell，应补上"读免问、写要问"的审批流 |
| **视觉模型仍有数据层面的天花板** | 任务一发现"同一车型名下多世代"导致的高置信度错误，任务二三无法解决 | 需要从数据标注粒度入手（按世代分层或细分子类） |

### 8.3 整体结论

三个任务串成了一条完整的链路：

```
任务一：自训练 51 类视觉模型（验证集 Macro-F1 = 0.9604）
   ↓ 封装为 CarEnsemble，提供 label_id / confidence / is_unknown / top_k
任务二：8 个工具的智能体，视觉识别必须经工具调用，支持连续调用与多轮对话
   ↓ 通过 ToolRegistry 暴露为 Function Calling schema
任务三：Web 系统，上传图片 → 对话 → 工具调用可视化 → 看车档案落库
```

**最终交付**：`classes.txt`（50 类）、`predictions.csv`（2,422 条）、
完整可运行的项目源代码（训练 / 推理 / 智能体 / 工具 / Web）、实训报告与说明文档。
